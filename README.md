# هویدا (HOVIDA)

**آنچه مهم است، روشن می‌شود.**
تحلیل هوشمند رزومه‌ها برای تصمیم‌های بهتر در منابع انسانی.

هویدا یک محصول SaaS فارسی‌محور برای تیم‌های جذب است: هر سازمان فضای کاری جداگانه دارد، برای هر «فرصت شغلی» معیارهای وزن‌دار و پرسش‌نامه اختصاصی می‌سازد، رزومه‌ها را بارگذاری می‌کند و فهرستی مرتب‌شده بر اساس **میزان تطابق** همراه با **شواهد مستقیم از متن رزومه** تحویل می‌گیرد. هوش مصنوعی فقط توصیف می‌کند؛ **تصمیم نهایی همیشه با انسان است.**

| **Google Calendar** | اتصال حساب گوگل هر فضای کاری با OAuth؛ تعیین جلسهٔ مصاحبه (عنوان، تاریخ شمسی، ساعت تهران، مدت، مصاحبه‌گران، مکان/Google Meet، توضیح) و ثبت رویداد در تقویم با ارسال دعوت‌نامه به کارجو؛ لغو جلسه رویداد گوگل را هم حذف می‌کند. بدون اتصال: جلسه در هویدا ذخیره و فایل ICS قابل دریافت است |
| **مقایسه** | تا ۴ کاندید یک فرصت، معیار به معیار با برجسته‌سازی بهترین مقدار و مهارت‌های مشترک |

| **گزارش‌ها** | روند رزومه‌ها، توزیع تطابق، قیف تصمیم‌گیری، دپارتمان‌ها، مهارت‌های پرتکرار و خروجی اکسل |
| **پیام‌ها** | پیش‌نویس دعوت به مصاحبه، درخواست اطلاعات، بانک استعداد و اعلام نتیجه با امضای سازمان (ارسال خودکار ندارد) |
| **جست‌وجوی سراسری** | `Ctrl/⌘ + K`؛ حساس نبودن به «ی/ي»، «ک/ك»، نیم‌فاصله و ارقام فارسی |

## اصول محصول

- **شواهد، نه حدس:** هر امتیاز معیار با نقل‌قول مستقیم از رزومه همراه است؛ نبود شاهد صریحاً گفته می‌شود.
- **هوش مصنوعی مطمئن جلوه نمی‌کند:** برچسب «پیشنهاد هویدا»، سطح اطمینان و یادآوری «تصمیم نهایی با شماست».
- **صداقت در نبود هوش مصنوعی:** پیشنهاد معیار بدون AI شکست صادقانه دارد و کاربر می‌تواند «الگوی آماده» را انتخاب کند؛ تحلیل رزومه با موتور محلی کلیدواژه‌ای و برچسب «تحلیل محلی» ادامه پیدا می‌کند.
- **بی‌طرفی:** نام، جنسیت، سن، وضعیت تأهل و ملیت در امتیاز اثری ندارد؛ آواتارها حروف اول نام‌اند، بدون حدس جنسیت.
- **بدون عدد ساختگی:** «زمان صرفه‌جویی‌شده» همیشه با برچسب «برآورد» و فرض محاسبه نمایش داده می‌شود.

## اجرای محلی

```bash
npm install
cp .env.example .env          # اختیاری: کلید هوش مصنوعی را تنظیم کنید
npm run dev                   # http://localhost:3000
```

بدون هیچ کلیدی هم برنامه کامل کار می‌کند (نسخه نمایشی، الگوهای آماده، موتور محلی).

### ساخت و اجرای نسخه production

```bash
npm run build                 # Vite (کلاینت) + esbuild (سرور) → dist/
NODE_ENV=production npm start
```

## پیکربندی (متغیرهای محیطی)

| متغیر | توضیح |
| --- | --- |
| `PORT` | پورت سرور (پیش‌فرض ۳۰۰۰) |
| `DATA_DIR` | محل ذخیره داده و فایل‌ها (پیش‌فرض `./data`) |
| `STORAGE_DRIVER` | `fs` (پیش‌فرض، دیسک `DATA_DIR`) یا `remote` (ذخیره‌ساز راه دور؛ روی Cloudflare خودکار تنظیم می‌شود و داده‌ها در R2 می‌مانند) |
| `STORAGE_URL`، `STORAGE_TOKEN` | نشانی ذخیره‌ساز راه دور و توکن اختیاری آن (فقط با `STORAGE_DRIVER=remote`) |
| `APP_SECRET` | کلید امضای پیوندهای فایل و رمزنگاری کلیدهای هوش مصنوعی؛ اگر خالی باشد خودکار ساخته و کنار داده‌ها (`DATA_DIR` یا R2) نگهداری می‌شود. **ثابت نگهش دارید** (تغییرش کلیدهای ثبت‌شده را ناخوانا می‌کند؛ هنگام انتقال سرور همان مقدار قبلی را بگذارید) |
| `ADMIN_EMAILS` | ایمیل(های) مدیران سامانه، جدا با ویرگول؛ این حساب‌ها به `/admin` دسترسی دارند |
| `AI_PROVIDER` | `auto` (پیش‌فرض)، `gemini`، `openai` یا `off` (خاموشی کامل، حتی کلیدهای پنل مدیریت) |
| `GEMINI_API_KEY`، `GEMINI_MODEL` | (اختیاری) کلید Gemini روی سرور؛ پشتیبانِ کلیدهای پنل مدیریت |
| `OPENAI_API_KEY`، `OPENAI_BASE_URL`، `OPENAI_MODEL` | (اختیاری) هر سرویس سازگار با OpenAI، از جمله درگاه‌های داخلی |
| `DISABLE_DEMO=1` | غیرفعال کردن نسخه نمایشی |
| `LEGACY_OWNER_EMAIL` | ایمیل حسابی که داده‌های نسخه قدیمی (تک‌سازمانی) را تحویل می‌گیرد؛ بدون آن، این داده‌ها به هیچ‌کس نشان داده نمی‌شوند |
| `CLIENT_IP_HEADER` | سرآیندی که لبه شبکه با IP واقعی کاربر پر می‌کند (پشت Cloudflare: `cf-connecting-ip`)؛ روی Render خودکار همین است |
| `TRUST_PROXY_HOPS` | اگر سرآیند بالا نباشد: تعداد پراکسی‌های جلوی سرور برای خواندن `X-Forwarded-For` از راست (پیش‌فرض ۱؛ بدون پراکسی ۰) |

روش پیشنهادی: کلیدها را در **پنل مدیریت › کلیدهای هوش مصنوعی** ثبت کنید (تا ۵ کلید با جابه‌جایی خودکار). کلیدهای متغیرهای محیطی همچنان کار می‌کنند و بعد از کلیدهای پنل استفاده می‌شوند. کلیدها هرگز به مرورگر ارسال نمی‌شوند. سرویس OpenAI-compatible با JSON mode و ارسال تصویر/PDF کار می‌کند و اگر درگاهی از فایل یا JSON mode پشتیبانی نکند، خودکار با متن استخراج‌شده دوباره تلاش می‌کند.

## پنل مدیریت سامانه (`/admin`)

اولین مدیر سامانه به یکی از این دو روش تعیین می‌شود:

1. **متغیر `ADMIN_EMAILS`:** ایمیل خود را تنظیم کنید و **بلافاصله** با همان ایمیل ثبت‌نام کنید (حتی وقتی ثبت‌نام عمومی بسته است، این ایمیل‌ها اجازه دارند)؛ `/admin` باز می‌شود. ایمیل‌ها تأیید نمی‌شوند، پس تا وقتی با آن ایمیل حسابی ساخته نشده، سرور در لاگ هشدار می‌دهد و کد راه‌اندازی را هم چاپ می‌کند. مدیر یک فضای کاری نمی‌تواند با این ایمیل‌ها عضو بسازد.
2. **کد راه‌اندازی یک‌بارمصرف:** تا وقتی هیچ مدیری وجود ندارد، سرور هنگام شروع کدی مثل `HV-XXXX-XXXX-XXXX` در لاگ چاپ می‌کند؛ وارد حساب خود شوید، به `/admin` بروید و کد را وارد کنید.

پس از آن، مدیران دیگر را از بخش «کاربران» تعیین کنید. همه تغییرات پنل در «گزارش رویدادها» با نام انجام‌دهنده ثبت می‌شود؛ «ورود پشتیبانی» یک نشست دوساعته و برچسب‌دار در زبانه جداگانه باز می‌کند (حتی برای فضای کاری تعلیق‌شده)، به خود پنل دسترسی ندارد و هر کاری در آن با نام «پشتیبانی هویدا» در فعالیت‌های همان فضای کاری ثبت می‌شود.

## استقرار روی Cloudflare (پیشنهادی)

هویدا کامل روی Cloudflare اجرا می‌شود: صفحه‌ها از لبه شبکه Cloudflare (Workers)، سرور Node در **Cloudflare Containers** و داده‌ها و فایل‌های رزومه در **R2**. پیکربندی آماده است (`wrangler.jsonc`، `Dockerfile`، `cloudflare/`). راهنمای گام‌به‌گام فارسی — دامنه، تنظیمات، اتصال GitHub، انتقال داده‌ها از Render و هزینه برآوردی — در [`docs/DEPLOY-CLOUDFLARE.md`](docs/DEPLOY-CLOUDFLARE.md) است.

> آدرس‌های `*.workers.dev` در ایران فیلتر هستند؛ برای کاربران داخل ایران دامنه اختصاصی را به Worker وصل کنید.

## استقرار با Docker (هر سرور دیگری)

```bash
docker build -t hovida .
docker run -p 8080:8080 -v hovida-data:/app/data -e APP_SECRET=… -e ADMIN_EMAILS=you@company.ir hovida
```

## استقرار روی Render

فایل `render.yaml` آماده است (دیسک دائمی ۱ گیگابایت روی `data/`). پس از استقرار، `ADMIN_EMAILS` را تنظیم کنید (یا کد راه‌اندازی را از لاگ بردارید) و کلیدهای هوش مصنوعی را در پنل مدیریت ثبت کنید.

> **مهاجرت از نسخه قدیمی:** فایل `data/screening-store.json` در اولین اجرا خودکار به ساختار جدید منتقل می‌شود (نشست‌ها ← فرصت‌های شغلی؛ رزومه‌های حذف‌شده واقعاً پاک می‌شوند). این داده‌ها اطلاعات شخصی کاندیداها هستند، پس **فقط** به حسابی داده می‌شوند که ایمیلش در `LEGACY_OWNER_EMAIL` آمده است — چه همان ایمیل بعداً ثبت‌نام کند، چه از قبل حساب داشته باشد (کافی است متغیر را تنظیم و سرویس را یک بار دوباره راه‌اندازی کنید). تا آن زمان داده‌ها پنهان می‌مانند و سرور در لاگ راهنمایی می‌کند.

## امنیت

- رمزهای عبور با **scrypt** و نمک تصادفی؛ نشست‌ها توکن‌های تصادفی که فقط هش SHA-256 آن‌ها ذخیره می‌شود؛ تغییر رمز، نشست‌های دیگر را می‌بندد.
- جداسازی سازمان‌ها در تمام پرس‌وجوها؛ رکورد سازمان دیگر دقیقاً مثل رکورد ناموجود رفتار می‌کند.
- فایل‌ها فقط با **پیوند امضاشده HMAC و ده‌دقیقه‌ای** باز می‌شوند (توکن نشست هرگز در URL نمی‌آید).
- محدودیت نرخ برای ورود، ثبت‌نام و نسخه نمایشی؛ حذف واقعی رزومه و فایل اصلی.
- کلیدهای هوش مصنوعی با AES-256-GCM (کلید مشتق از `APP_SECRET`) ذخیره می‌شوند و API فقط بخش کوتاهی از آن‌ها را نشان می‌دهد.
- فایل‌های بارگذاری‌شده (HTML، SVG و…) هرگز در دامنه برنامه اجرا نمی‌شوند: فقط PDF، تصویر و متن ساده قابل پیش‌نمایش‌اند و بقیه به‌صورت دانلود با `Content-Security-Policy: sandbox` ارسال می‌شوند.

## آزمون‌ها

```bash
npm run lint                  # tsc --noEmit
npm test                      # منطق خالص، خواندن همه قالب‌ها، رفتار هوش مصنوعی، جابه‌جایی خودکار کلیدها، مهلت و لغو درخواست‌ها، ذخیره‌سازی
npm run build && npm run test:admin   # آزمون سرتاسری نسخه production: پنل مدیریت، کلیدها، اتصال‌ها، قالب‌ها و تنظیمات
npm run test:integrations     # جست‌وجوی لینکدین با سرویس ساختگی، ارسال واقعی ایمیل روی SMTP آزمایشی، جلسهٔ مصاحبه و ICS
npm run build && npm run test:backup  # پشتیبان کامل و بازیابی سرتاسری (دیسک → ذخیره‌ساز راه دور)
npm run build && npm run test:cloudflare   # Worker، مسیریابی لبه و R2 در محیط واقعی workerd (بدون Docker)
# با یک سرور در حال اجرا روی 3111:
DATA_DIR=/tmp/hv PORT=3111 NODE_ENV=production node dist/server.cjs &
npm run test:api              # آزمون سرتاسری API: احراز هویت، جداسازی سازمان‌ها، فایل‌ها، تحلیل
BASE=http://127.0.0.1:3111 npm run test:mount   # اجرای واقعی اپ در jsdom
```

### نمایش محلی اتصال‌ها بدون سرویس واقعی

```bash
node scripts/mock-linkedin.mjs --port 9911 &   # سرویس جست‌وجوی ساختگی (افراد داستانی)
node scripts/mock-apify.mjs --port 9922 &     # پلتفرم Apify ساختگی (Actor جست‌وجوی پروفایل)
node scripts/mock-smtp.mjs --port 2525 &       # صندوق SMTP آزمایشی: پیام‌ها فقط چاپ می‌شوند
LINKEDIN_API_URL=http://127.0.0.1:9911/search LINKEDIN_ACCESS_TOKEN=demo npm run dev
```

سرویس جست‌وجو را در `/admin` › «اتصال‌ها» با آدرس `http://127.0.0.1:9911/search` و توکن `demo` ثبت کنید (یا همان دو
متغیر محیطی بالا را بگذارید)، و صندوق ایمیل را در «تنظیمات ← اتصال‌ها» با سرور `127.0.0.1`، پورت `2525`، اتصال امن خاموش.
هیچ ایمیل واقعی ارسال نمی‌شود و هیچ دادهٔ واقعی لینکدین خوانده نمی‌شود.
