# بازارچهٔ آزمون — آزمون‌هایی که بیرون از هویدا برگزار می‌شوند

> بانک آزمون خود هویدا (قضاوت موقعیتی، نمونه‌کار، رفتار کاری) در
> [`ASSESSMENT.md`](ASSESSMENT.md) است. این سند برای حالت دیگری است: سازمان از قبل با
> یک مرکز سنجش قرارداد دارد — آزمون زبان، شخصیت کاری، آزمون کتبی با ناظر — و می‌خواهد
> دعوت و نتیجه در همان پروندهٔ کارجو بماند.

---

## ۱. سه چیزی که این ماژول انجام می‌دهد

1. **فهرست سرویس‌ها** — مدیر فضای کاری، سرویس و آزمون‌هایش را یک‌بار وارد می‌کند (تنظیمات ←
   بازارچهٔ آزمون). هیچ سرویسی از پیش نصب نیست و هیچ فهرست آزمونی از طرف ما نمی‌آید.
2. **دعوت** — هنگام ساخت آزمون برای یک کارجو، آزمون بیرونی انتخاب می‌شود؛ هویدا دعوت را
   نگه می‌دارد و با دکمهٔ «ارسال»، لینک را از **صندوق سازمان** می‌فرستد.
3. **بازگشت نتیجه** — سرویس با یک کلید باریک نتیجه را ثبت می‌کند، یا اگر API ندارد، منابع
   انسانی خودش نمره/یادداشت را وارد می‌کند. در هر دو حالت رکورد می‌گوید **«نتیجهٔ بیرونی»** و
   نام سرویس را می‌نویسد.

---

## ۲. دو حالت اتصال

| حالت | چه کسی جلسه را می‌سازد | مناسب برای |
| --- | --- | --- |
| `api` | خودِ هویدا، با `POST {baseUrl}{sessionPath}` | سرویسی که API دارد و می‌تواند برای هر کارجو لینک یکتا بسازد |
| `link` | منابع انسانی، با چسباندن لینک همان کارجو | مراکز سنجش ایرانی که API عمومی ندارند |

در حالت `link`، هویدا فقط لینک را می‌فرستد و نتیجه را دستی ثبت می‌کند؛ هیچ ادعای اتصال
خودکار در آن پرونده نوشته نمی‌شود.

---

## ۳. قرارداد (چیزی که به توسعه‌دهندهٔ سرویس می‌دهید)

### ۳٫۱ بررسی سلامت

```http
GET {baseUrl}{checkPath}          # پیش‌فرض /health
Authorization: Bearer <کلید سرویس>
```

هر پاسخ `2xx` = سالم. هر چیز دیگر = ناموفق، و **همان کد و متن** در کارت سرویس می‌ماند.

### ۳٫۲ ساخت جلسه

```http
POST {baseUrl}{sessionPath}       # پیش‌فرض /sessions
Authorization: Bearer <کلید سرویس>
Content-Type: application/json

{
  "testId": "lang-1",
  "testName": "زبان سازمانی",
  "candidate": { "name": "سارا محمدی", "email": "sara@example.ir" },
  "externalRef": "ext_wqkHqRpVT_HX",
  "expiresAtISO": "2026-11-27T08:20:00.000Z"
}
```

پاسخ مورد انتظار:

```json
{ "id": "sess_123", "url": "https://tests.example.com/t/abc" }
```

قواعد سخت:

- `url` باید **https** باشد (به‌جز loopback برای آزمون خودمان)؛ لینک غیر https هرگز برای کارجو
  فرستاده نمی‌شود و ارسال با `PROVIDER_BAD_URL` شکست می‌خورد.
- پاسخ نامعتبر (`200` با متن غیر JSON، یا بدون `url`) شکست است، نه «شاید کار کرده».
- **هیچ داده‌ای جز نام، ایمیل، شناسهٔ دعوت و مهلت فرستاده نمی‌شود.** نه متن رزومه، نه تلفن،
  نه شناسهٔ داخلی کارجو.

### ۳٫۳ ثبت نتیجه

```http
POST /api/v1/results
Authorization: Bearer <کلید هویدا با scope=assessments>
Content-Type: application/json

{
  "externalRef": "ext_wqkHqRpVT_HX",
  "score": 82,
  "dimensions": [{ "id": "reading", "label": "خواندن", "score": 88 }],
  "note": "گزارش کامل در سرویس ارائه‌دهنده."
}
```

پاسخ: `{ assessment: { id, externalRef, providerName, status, source, score, band, dimensions, completedAtISO } }`

- `score` بین ۰ تا ۱۰۰، اختیاری؛ `dimensions` اختیاری؛ `note` می‌تواند تنها محتوا باشد
  («سطح B۲ — قبول»). اگر هیچ‌کدام نباشد → `400 NO_RESULT`.
- یک دعوت **یک** نتیجه می‌گیرد؛ دومی `409 ALREADY_COMPLETED` است.
- `externalRef` به فضای کاری خودش گره خورده است: کلید دیگر، همان شناسه را `404` می‌گیرد.
- دعوت آزمون‌های **خود هویدا** از این در نمی‌آید (`409 NOT_PROVIDER_TEST`).

## ۴. وضعیت‌ها (چرا «آماده» تنها با واقعیت می‌آید)

| وضعیت | معنا | ارسال؟ |
| --- | --- | --- |
| `unconfigured` | نشانی/کلید/آزمون کم است | نه — `409 PROVIDER_NOT_READY` با همان دلیل |
| `unchecked` | نشانی و کلید هست، اما هیچ درخواستی موفق نشده | نه |
| `degraded` | آخرین بررسی ناموفق بود (کد HTTP یا خطای شبکه ذخیره می‌شود) | نه |
| `ready` | آخرین بررسی `2xx` بود | بله |

حالت `link` بدون هیچ درخواستی `ready` است، چون چیزی برای بررسی وجود ندارد.

---

## ۵. امنیت

- کلید سرویس با **AES-256-GCM** (کلید مشتق‌شده از `APP_SECRET`) ذخیره می‌شود؛ در هیچ پاسخ
  API برنمی‌گردد و فقط چهار نویسهٔ آخرش نمایش داده می‌شود. اسنپ‌شات روی دیسک فقط
  `apiKeyEnc` را دارد.
- نشانی باید **https** باشد (جز loopback) — کلید روی http فرستاده نمی‌شود.
- تغییر نشانی، کلید قبلی را باطل می‌کند؛ کلید برای همان میزبان صادر شده بود.
- درخواست‌های خروجی با **۹ ثانیه** مهلت و `redirect: error` انجام می‌شوند (تغییر مسیر
  ناگهانی به میزبان دیگر، کلید را لو نمی‌دهد).
- `scope: assessments` تنها درِ نوشتن است؛ خواندن رزومه، تصمیم و ارسال ایمیل با آن ممکن نیست.
- نوشتن (ساخت/ویرایش/حذف/بررسی) فقط برای مدیر؛ خواندن برای همهٔ اعضا.

## ۶. رفتار در خطا (چیزی که در تست هم ثابت شده)

| رخداد | نتیجه |
| --- | --- |
| سرویس `500` برگرداند | `502 PROVIDER_FAILED` با کد و متن سرویس؛ **هیچ ایمیلی نمی‌رود** |
| پاسخ JSON خوانا نبود | `502 PROVIDER_BAD_RESPONSE` |
| پاسخ `url` نداشت | `502 PROVIDER_NO_URL` |
| `url` غیر https بود | `502 PROVIDER_BAD_URL` |
| مهلت یا DNS/اتصال | `502 PROVIDER_TIMEOUT` / `PROVIDER_UNREACHABLE` |
| کلید رمزگشایی نشد (تغییر `APP_SECRET`) | `409 KEY_UNREADABLE` و درخواست «کلید را دوباره وارد کنید» |
| ارسال دوبارهٔ همان دعوت | همان جلسه دوباره استفاده می‌شود؛ جلسهٔ دوم ساخته نمی‌شود |
| صندوق سازمان وصل نیست | `409 EMAIL_NOT_CONFIGURED` و **پیش از** تماس با سرویس بررسی می‌شود |
| سرویس بعد از ساخت دعوت حذف شد | `409 PROVIDER_GONE` (نتیجهٔ ثبت‌شده سر جایش می‌ماند) |

## ۷. در رابط کاربری

- **تنظیمات ← بازارچهٔ آزمون**: کارت هر سرویس با وضعیت، میزبان، چهار نویسهٔ کلید، تعداد دعوت و
  نتیجه، زمان و تأخیر آخرین بررسی، دکمهٔ «بررسی اتصال»، ویرایش و برداشتن. قرارداد HTTP
  روی همان صفحه چاپ می‌شود تا بدون پرسیدن از ما قابل پیاده‌سازی باشد.
- **دیالوگ آزمون در پروندهٔ کارجو**: آزمون‌های داخلی و بیرونی کنار هم؛ هر آزمون بیرونی می‌گوید
  «در سرویس سازمان شما برگزار می‌شود». برای حالت `link` جای لینک همان کارجو باز می‌شود؛ برای
  نتیجهٔ دستی، فرم «ثبت نتیجه» (نمرهٔ اختیاری + یادداشت).
- **صفحهٔ کارجو (`/assess/:token`)**: نام سرویس، توضیح یک‌خطی و دکمهٔ «رفتن به آزمون»؛ هیچ
  سؤالی نمایش داده نمی‌شود و ثبت پاسخ روی صفحهٔ ما رد می‌شود.

## ۸. آنچه این نیست

| نیست | چرا |
| --- | --- |
| بازارچهٔ رسمی با فهرست فروشندگان و قیمت | ما با هیچ مرکز سنجشی قرارداد نداریم؛ فهرست ساختگی، دروغ است |
| واسطهٔ پرداخت برای آزمون | پرداخت با قرارداد خود مشتری است؛ هویدا فقط دعوت و نتیجه را جابه‌جا می‌کند |
| اجرای آزمون در مرورگر کارجو | آزمون در سرویس برگزار می‌شود؛ صفحهٔ ما فقط راه می‌دهد |
| خرید خودکار آزمون از API سرویس | نیازمند قرارداد و اعتبار در حساب مشتری است؛ ساختار `sessionPath` آماده است ولی ما از طرف کسی خرید نمی‌کنیم |
| تفسیر بالینی نتیجه | ما نمره و ابعاد را همان‌طور که رسیده نگه می‌داریم؛ خواندنش کار انسان است |

## ۹. آزمون خودکار

`npm run test:marketplace` — ۸۷ بررسی با یک سرویس نمونهٔ واقعی (HTTP در همان پروسه):

- نبود سرویس پیش‌فرض، خلاصهٔ صفر، قرارداد؛
- رد شدن عضو و نشانی غیر https و حالت `api` بدون کلید؛
- کلید در پاسخ نیست، در اسنپ‌شات روی دیسک هم نیست؛
- `unchecked` → بررسی سالم → `ready`؛ `503` → `degraded` با متن، و ارسال دوباره بسته می‌شود؛
- ساخت دعوت بدون تماس با سرویس؛ ارسال بدون صندوق → `EMAIL_NOT_CONFIGURED` و صفر تماس؛
- ارسال موفق: یک جلسه، شناسهٔ آزمون درست، ایمیل کارجو، `externalRef`، نام سرویس در متن ایمیل؛
- ارسال دوباره، جلسهٔ دوم نمی‌سازد؛
- `500` / JSON نامعتبر / `url` غیر https / بدون `url` / پورت بسته — همه شکست صادقانه و بدون ایمیل؛
- حالت `link`: لینک اجباری، https اجباری، ایمیل با همان لینک، نتیجهٔ دستی («سطح B۲ — قبول»);
- صفحهٔ عمومی: نام سرویس، لینک بیرونی، بدون سؤال، رد کردن ثبت پاسخ؛
- `POST /api/v1/results`: کلید خواندنی ۴۰۳، `externalRef` ناشناس ۴۰۴، نتیجهٔ درست، تکرار ۴۰۹،
  جداسازی فضای کاری، رد کردن آزمون داخلی، «بدون نتیجه» ۴۰۰;
- رویداد وب‌هوک `assessment.completed` و حذف رویداد ناشناس؛
- حذف سرویس: نتیجه‌ها می‌مانند، دعوت ارسال‌نشده `PROVIDER_GONE` می‌دهد.
