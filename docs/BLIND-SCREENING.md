# غربالگری بی‌طرف (پنهان‌سازی هویت)

> **چکیده:** وقتی روشن است، در همهٔ نماهای غربالگری نام، ایمیل، تلفن، پیوند پروفایل و
> فایل اصلی کارجو **پنهان** می‌شود و کارجو با یک برچسب پایدار («کارجوی ۲۴۸۱») شناخته
> می‌شود. امتیاز، معیارها، شاهدهای متنی و سابقه کامل می‌مانند — چیزی که برای تصمیم لازم
> است پنهان نمی‌شود؛ فقط هویت می‌رود. برای تماس با کارجو (ایمیل، پیامک، مصاحبه، پیشنهاد،
> نظرسنجی) اول باید هویت را **آشکار** کنید، و همان لحظه با نام شما در تاریخچه ثبت می‌شود.

---

## ۱. کجا روشن می‌شود؟

**تنظیمات › سازمان › کارت «غربالگری بی‌طرف»** — فقط مدیر یا مالک فضای کاری. پیش‌فرض
**خاموش** است: تیم کوچکی که کارجوهایش را می‌شناسد به آن نیاز ندارد، و روشن‌شدن ناگهانی
وسط یک استخدام باید غیرممکن باشد. روشن و خاموش‌کردن هر دو در فعالیت‌های تیم ثبت می‌شوند.

| با روشن‌بودن پنهان می‌شود | دست‌نخورده می‌ماند |
| --- | --- |
| نام و نام خانوادگی (جای آن برچسب «کارجوی ۲۴۸۱») | امتیاز و دستهٔ تطبیق |
| ایمیل، تلفن، پروفایل لینکدین | معیارها، وزن‌ها، امتیاز هر معیار |
| نام فایل رزومه و فایل اصلی (PDF/Word) | شاهدهای متنی و خلاصه (با ماسک نام) |
| شهر؟ نه — شهر می‌ماند (کمک به تصمیم، کم‌شناسا) | سابقه، مهارت، سال تجربه، دانشگاه و شرکت‌ها |

> **صادقانه:** پنهان‌سازی، هویت را می‌پوشاند نه نشانه‌های غیرمستقیم را. اگر رزومه
> «کارشناس ارشد شبکه در شرکت الف» باشد، ممکن است همان یک نفر را لو بدهد. این ابزار برای
> **کم‌کردن سوگیری** است، نه ادعای ناشناس‌بودن مطلق. در جلسه هم همین را می‌گوییم.

## ۲. پنهان‌سازی کجاست؟ روی سرور، نه در مرورگر

این مهم‌ترین تصمیم طراحی است: اگر فیلد در پاسخ JSON باشد و فقط در صفحه پنهان شود، هر
کسی با یک نگاه به تب Network نام را می‌بیند. پس نسخهٔ **پاک‌شده** ساخته می‌شود و همان
فرستاده می‌شود:

| مسیر | چه می‌شود |
| --- | --- |
| `GET /api/resumes` | هر ردیف بی‌نام، بدون ایمیل/تلفن/پیوند، `filePath` و `fileHash` تهی |
| `GET /api/resumes/:id` | همان، به‌علاوهٔ ماسک‌شدن متن رزومه، خلاصه، شاهدها و دلیل دسته |
| `GET /api/resumes/compare` | همان بی‌نام‌سازی |
| `GET /api/dashboard` | صف «منتظر تصمیم» و فعالیت‌ها ماسک می‌شوند |
| `GET /api/activity` | «… را تأیید کرد» با «نام» جای‌گذاری می‌شود |
| `GET /api/search` | نتیجه‌ها بی‌نام؛ جست‌وجو با نام، نام را تأیید نمی‌کند |
| `GET /api/talent/list` | بانک استعداد هم بی‌نام |
| `GET /api/resumes/:id/comments` | یادداشت‌های تیمی هم ماسک می‌شوند (ممکن است کسی نام را در متن نوشته باشد) |
| `GET /api/v1/candidates` (API) | کلید API همان چیزی را می‌بیند که مرورگر: بدون هویت |
| `GET /api/resumes/:id/file-url` و `/files/:id` | فایل اصلی بسته است (لینک امضاشدهٔ قبلی هم کار نمی‌کند) |

ماسک متن، نام را **توکن‌به‌توکن** می‌پوشاند («مینا رضایی» → «نام»)، نه با جست‌وجوی
ساده‌لوحانه: پیوندها «پیوند»، ایمیل‌ها «ایمیل» و شماره‌ها (فارسی یا لاتین) «تلفن» می‌شوند.
واژه‌های بی‌ربط دست نمی‌خورند (تست واحد این را نگه می‌دارد).

## ۳. کارهایی که تا آشکارسازی بسته‌اند

هر عملی که به کارجو **می‌رسد**، با `409 BLIND_REVEAL_REQUIRED` برمی‌گردد:

- نوشتن پیام (`POST /messages/draft` و ارسال ایمیل سازمان)
- پیامک (`POST /integrations/sms/send`)
- تعیین جلسهٔ مصاحبه (`POST /interviews`)
- لینک انتخاب زمان (`POST /scheduling`)
- پیشنهاد شغلی (`POST /offers`)
- نظرسنجی تجربه (`POST /surveys`)

**باز است:** تصمیم تأیید/رد، یادداشت تصمیم، جابه‌جایی روی تختهٔ جذب، بانک استعداد،
مقایسه، بازبینی دقیق. یعنی غربالگری کامل انجام می‌شود؛ فقط تماس منتظر آشکارسازی است.

## ۴. آشکارسازی هویت

در پنل کارجو، بالای صفحه، دکمهٔ **«آشکارسازی هویت»** است. یک جمله دلیل (اختیاری) و تأیید؛
از آن لحظه همان کارجو با نام و راه تماس دیده می‌شود و:

- در **فعالیت‌های تیم** یک ردیف با نوع «آشکارسازی هویت» ثبت می‌شود: چه کسی، کدام کارجو، چه دلیلی.
- آشکارسازی **فقط برای همان کارجو و همان اقدام** است؛ فهرست برای بقیه بی‌نام می‌ماند.
- با خاموش‌کردن کلید، هویت همه دوباره دیده می‌شود.

## ۵. API

| مسیر | نقش | کار |
| --- | --- | --- |
| `PATCH /api/org { blindScreening: true\|false }` | مدیر/مالک | روشن/خاموش؛ در تاریخچه ثبت می‌شود |
| `POST /api/resumes/:id/reveal { reason }` | هر عضو | نسخهٔ کامل را برمی‌گرداند و ردیف تاریخچه می‌سازد (`409 BLIND_OFF` اگر خاموش باشد) |
| همهٔ مسیرهای فهرست | — | با روشن‌بودن، نسخهٔ پاک‌شده (`blindHidden: true`) |

## ۶. چه چیزی این نیست

- **حذف داده نیست.** رکورد کامل سر جای خود است؛ این یک **نما** است (مثل ناشناس‌سازی
  نگه‌داری داده که آن یکی واقعاً داده را می‌برد — `docs/DATA-RETENTION.md`).
- **تضمین بی‌طرفی نیست.** جلوی سوگیری هویتی را می‌گیرد؛ سوگیری معیارها جای دیگری است.
- **اجباری نیست.** تیم خودش تصمیم می‌گیرد؛ بعضی مشتریان می‌خواهند، بعضی نه.

## ۷. تست

```bash
npm run test:blind   # ۳۹ بررسی سرتاسری: پنهان‌سازی، بسته‌بودن تماس‌ها، آشکارسازی، خاموش‌کردن
npm test             # شامل ۱۶ بررسی واحد ماسک، برچسب و نسخهٔ پاک‌شده
npm run test:mount   # ۱۲ بررسی رابط: کارت تنظیمات، جدول بی‌نام، پنل، آشکارسازی
```
