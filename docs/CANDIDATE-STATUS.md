# پیگیری درخواست (صفحهٔ وضعیت کارجو)

> بیشتر کارجویان بعد از تماس اول دو هفته هیچ خبری نمی‌شنوند و درست هم فرض می‌کنند که
> نادیده گرفته شده‌اند. یک لینک که بگوید «در حال بررسی رزومه» همان شک را برمی‌دارد، بدون
> اینکه یک دقیقه وقت اضافه از منابع انسانی بگیرد.

جای این قابلیت در سایت: پروندهٔ کارجو → تب **بیشتر** → **پیگیری درخواست**.
صفحهٔ عمومی: `/status/<توکن>`.

---

## ۱. چه چیزی می‌بیند؟

یک صفحهٔ ساده و بدون ورود، با این چهار چیز و نه بیشتر:

1. نام سازمان، عنوان موقعیت و نام کارجو
2. وضعیت امروز با زبان کارجو — نه نام ستون تختهٔ جذب
3. مسیر درخواست: پنج گام که انجام‌شده/جاری/بعدی مشخص است
4. تاریخ آخرین به‌روزرسانی، مصاحبهٔ بعدی (اگر رزرو شده باشد)، ایمیل تماس و تاریخ اعتبار لینک

| وضعیت | پیام |
| --- | --- |
| `received` | «درخواست ثبت شد» — در نوبت بررسی است |
| `screening` | «در حال بررسی» — چند روز کاری طول می‌کشد |
| `interview` | «مرحلهٔ مصاحبه» — جزئیات زمان از طریق ایمیل/پیامک |
| `offer` | «پیشنهاد شغلی» — آماده یا ارسال شده |
| `hired` | «استخدام» — هماهنگی روز اول با منابع انسانی |
| `closed` | «بسته شد» — با تشکر و دعوت به گرفتن بازخورد |

**نکتهٔ عمدی:** وضعیت بسته هرگز «رد شد» نوشته نمی‌شود و دلیل تصمیم هم نمی‌آید. دلیل رد
شدن یک گفت‌وگوست، نه یک خط در یک صفحهٔ وب.

## ۲. چه چیزی هرگز در این صفحه نیست؟

- امتیاز تطبیق، معیارها یا امتیاز مصاحبه
- یادداشت‌های داخلی، کارت ارزیابی، نظر مصاحبه‌گر
- نام مصاحبه‌گرها یا اعضای تیم
- اطلاعات سایر کارجویان
- فایل رزومه یا شمارهٔ تماس کارجو
- دلیل تصمیم

آزمون خودکار همین را چک می‌کند: پاسخ API با فهرستی از کلیدواژه‌های حساس مقایسه می‌شود
(`score`، `note`، `interviewer`، ایمیل کارجو و …) و هیچ‌کدام نباید در بدنه باشد.

## ۳. قواعد لینک

| قاعده | رفتار |
| --- | --- |
| ساخت | توکن تصادفی ۲۴ بایتی (base64url)؛ حدس‌زدنی نیست |
| تعداد | برای هر کارجو فقط **یک لینک فعال**؛ ساخت لینک تازه، لینک قبلی را همان لحظه غیرفعال می‌کند |
| لغو | دکمهٔ سطل در همان پنجره؛ صفحه فوراً `410 LINK_REVOKED` می‌دهد |
| اعتبار | ۱۲۰ روز از زمان ساخت؛ بعد از آن `410 LINK_EXPIRED` |
| بازدید | هر باز شدن شمرده می‌شود؛ منابع انسانی می‌بیند کارجو صفحه را دیده یا نه |
| توکن نامعتبر | `404 LINK_NOT_FOUND` با پیام روشن، نه صفحهٔ سفید |
| حذف کارجو | با حذف دادهٔ کارجو (DSAR) لینک‌ها هم پاک می‌شوند و در شمارش می‌آیند |
| حذف آگهی | لینک زنده می‌ماند ولی دیگر نام آگهی را نشان نمی‌دهد |

## ۴. مرزهای دسترسی

- ساخت و فهرست لینک‌ها فقط از پروندهٔ همان کارجو و با همان قاعدهٔ **دسترسی هر آگهی**
  (۴۰۳ اگر آگهی برای شما اشتراک گذاشته نشده باشد).
- در حالت **غربالگری بی‌طرف**، ساخت لینک شخصی بسته است (`409 BLIND_REVEAL_REQUIRED`)؛
  لینکی که قبلاً داده شده و در دست کارجوست، کار خودش را می‌کند.
- هر فضای کاری فقط لینک‌های خودش را می‌بیند؛ توکن یک فضای کاری در فضای دیگر معنا ندارد.

## ۵. API

| متد و مسیر | کار |
| --- | --- |
| `POST /api/resumes/:id/status-link` | ساخت (و غیرفعال‌کردن لینک قبلی) |
| `GET /api/resumes/:id/status-links` | فهرست لینک‌ها با تعداد بازدید |
| `DELETE /api/status-links/:id` | لغو لینک |
| `POST /api/status-links/:id/send` | فرستادن لینک با ایمیل سازمان (فقط با کلیک انسان) |
| `GET /api/status/:token` | صفحهٔ عمومی؛ بدون نشست، بدون هیچ هدر احراز هویت |

پاسخ عمومی دقیقاً همان ساختار `PublicStatus` است: `orgName`، `candidateName`، `jobTitle`،
`state`، `message`، `steps[]`، `updatedAtJalali`، `expiresAtJalali`، `nextInterviewJalali`،
`contactEmail`.

## ۶. ارسال لینک

دو راه، هر دو با تصمیم انسان:

1. **کپی و فرستادن دستی** — دکمهٔ «کپی لینک» نشانی مطلق (با دامنه) را در کلیپ‌بورد می‌گذارد؛
   در پیام، پیامک یا هر جای دیگری برای کارجو بفرستید.
2. **«فرستادن با ایمیل سازمان»** — همان پنجره، همان لینک، از صندوق ایمیل خودِ سازمان به نشانی
   ثبت‌شدهٔ کارجو. متن نامه کوتاه است: نام کارجو، عنوان موقعیت، لینک، تاریخ اعتبار — بدون
   امتیاز، یادداشت یا دلیل تصمیم.

قاعده‌های ارسال (همه از سرور، نه از رابط کاربری):

| وضعیت | پاسخ |
| --- | --- |
| ساخت لینک | **هیچ نامه‌ای نمی‌رود** — ساخت و ارسال دو کار جدا هستند |
| صندوق ایمیل وصل نیست | `409 EMAIL_NOT_CONFIGURED` + «از تنظیمات ← اتصال‌ها وصل کنید» |
| ایمیل کارجو ثبت نشده | `400 NO_CANDIDATE_EMAIL` + پیشنهاد فرستادن دستی |
| لینک لغو‌شده | `409 LINK_REVOKED` — اول «لینک تازه» |
| لینک منقضی | `409 LINK_EXPIRED` |
| غربالگری بی‌طرف روشن | `409 BLIND_REVEAL_REQUIRED` (نشانی کارجو هویت است) |
| سقف ارسال ساعتی پر | `429` |
| خطای SMTP | `502 SMTP_FAILED` با پیام فارسی روشن؛ نسخهٔ ناموفق در تاریخچهٔ کارجو می‌ماند |
| ارسال دوباره | مجاز — برای وقتی که کارجو می‌گوید نامه را ندیده |

هر ارسال در سه جا ثبت می‌شود: روی خود لینک (`sentAtISO` / `sentAtJalali` / `sentTo`)، در
تاریخچهٔ ایمیل‌های کارجو (با متن کامل)، و در فعالیت‌ها (`status.sent`).

**هیچ ارسال خودکاری وجود ندارد:** نه با ساخت لینک، نه با جابه‌جایی کارجو در تخته، نه با
زمان‌بند. اگر روزی «پیام خودکار مرحله» بخواهید، از مسیر اتوماسیون جذب می‌آید که خودش تأیید
انسانی دارد.

## ۷. آزمون

```bash
npm run test:status       # ۶۶ بررسی
```

پوشش: باز شدن بدون نشست، پیام درست در هر مرحله، تغییر خودکار با جابه‌جایی کارجو در تخته،
تاریخ مصاحبهٔ بعدی بدون افشای نام مصاحبه‌گر، زبان «بسته شد» به‌جای «رد شد»، حذف گام‌های
بعدی برای درخواست بسته، شمارش بازدید، یک‌فعال‌بودن لینک، لغو فوری، توکن نامعتبر، جداسازی
فضاهای کاری، مسدودی ساخت در حالت بی‌طرف، پاک‌سازی DSAR با شمارش، و نبود کلیدواژه‌های حساس
در پاسخ عمومی.

برای مسیر ایمیل، یک SMTP ساختگی درون تست بالا می‌آید و بررسی می‌شود: ساخت لینک صفر نامه
دارد، صندوق وصل‌نشده ۴۰۹ می‌دهد، لینک لغو‌شده فرستاده نمی‌شود، نامه واقعاً به ایمیل کارجو
می‌رسد و لینک را در خود دارد (با بازکردن soft line break های quoted-printable)، متن در
تاریخچهٔ کارجو ذخیره می‌شود، رمز SMTP هرگز برنمی‌گردد، ارسال دوباره مجاز است، `sentTo` روی
لینک می‌ماند، و در حالت بی‌طرف ارسال هم بسته است.
