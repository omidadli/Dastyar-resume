# نگه‌داری داده و درخواست دادهٔ شخصی (DSAR)

هر پروندهٔ استخدام، دادهٔ شخصی است. هویدا دو چیز را در اختیار تیم منابع انسانی می‌گذارد:

1. **سیاست نگه‌داری** — بعد از چند روز بی‌حرکتی، رکورد کارجو خودکار ناشناس یا حذف می‌شود.
2. **حق دسترسی و حذف** — برای یک کارجوی مشخص، همهٔ داده در یک فایل و در یک کلیک؛ یا پاک‌سازی کامل.

هر دو در **تنظیمات › سازمان** (سیاست) و **پروندهٔ کارجو › اطلاعات بیشتر** (DSAR) هستند، فقط با نقش مدیر، و هر دو در فید فعالیت تیم ثبت می‌شوند.

---

## ۱) سیاست نگه‌داری

**تنظیمات › سازمان › نگه‌داری داده**

| فیلد | معنی |
| --- | --- |
| مدت نگه‌داری (روز) | ۰ = خاموش (پیش‌فرض). حداکثر ۳۶۵۰ روز. پیشنهادهای سریع: ۹۰ / ۱۸۰ / ۳۶۵ / ۷۳۰ |
| وقتی مدت تمام شد | **ناشناس‌سازی** (پیشنهاد ما) یا **حذف کامل رکورد** |

### چه کسی مشمول می‌شود؟

کارجویی که **همهٔ** این شرط‌ها را دارد:

* در «بانک استعداد» نگه داشته نشده است؛
* در ستون «استخدام‌شده» نیست؛
* آخرین تغییر رکوردش قدیمی‌تر از پنجرهٔ سیاست است.

کارجوی استخدام‌شده یا عضو بانک استعداد **هرگز** مشمول نمی‌شود؛ برای آن‌ها فقط «پاک‌سازی کامل» در پروندهٔ همان کارجو (با تأیید صریح) وجود دارد.

### ناشناس‌سازی چه چیزی را پاک می‌کند؟

| پاک می‌شود | می‌ماند |
| --- | --- |
| نام، ایمیل، تلفن | امتیاز، دسته (تأیید/رد/بررسی)، رتبه |
| متن کامل رزومه و فایل PDF/Word | مهارت‌هاست، سال تجربه، عنوان شغلی |
| خلاصه، نقاط قوت/ضعف، شواهد نقل‌شده | دپارتمان، منبع (پورتال/معرفی/جست‌وجو) |
| یادداشت‌های تیم روی کارجو | تاریخ‌های تحلیل و تصمیم |
| متن ایمیل/پیامک فرستاده‌شده، نام گیرنده | وضعیت ارسال، زمان ارسال |
| نام کارجو در مصاحبه‌ها و پیشنهادها | زمان جلسه، عنوان پیشنهاد، شرایط |
| یادداشت مصاحبه‌گر در کارت ارزیابی | امتیاز معیارها |
| نام فایل (به `resume-xxxxxx.pdf` تغییر می‌کند) | شناسهٔ رکورد، برای پیوستگی گزارش |

یعنی گزارش‌ها و آمار «چند نفر غربال شد، چند نفر تأیید شد، میانهٔ زمان استخدام» دست‌نخورده می‌مانند، اما هیچ‌کس را نمی‌توان از داده‌های باقی‌مانده شناسایی کرد.

### حذف کامل رکورد

همهٔ موارد بالا و خود رکورد و فایل حذف می‌شوند (به‌همراه مصاحبه‌ها، پیشنهاد، لینک زمان‌بندی، پیام‌ها، یادداشت‌ها، کارت‌های ارزیابی و پیشنهادهای اتوماسیون مربوط به همان کارجو). **این کار برگشت‌پذیر نیست.**

### هزینهٔ استخدام در این سیاست

ردیف‌های «هزینهٔ استخدام» دادهٔ مالی سازمان‌اند، نه دادهٔ شخصی کارجو: تاریخ، نوع، مبلغ و
نوع شغلی دارند و هیچ نام یا تماسی در آن‌ها نیست. بنابراین:

- ناشناس‌سازی و حذف کامل یک کارجو به این ردیف‌ها دست نمی‌زند؛ عددهای مالی فصل نباید با
  یک درخواست DSAR جابه‌جا شوند.
- با حذف کل فضای کاری، ردیف‌های هزینه و نرخ ساعتی هم پاک می‌شوند (مثل بقیهٔ داده‌های
  همان فضا).

### اجرا

| راه | چه وقت |
| --- | --- |
| **اجرای آزمایشی** | فهرست رکوردهایی که مشمول می‌شوند را نشان می‌دهد؛ هیچ چیزی تغییر نمی‌کند |
| **اجرای الآن** | با تأیید صریح، همان لحظه اجرا می‌شود |
| **اجرای خودکار** | سرور هر ساعت بررسی می‌کند؛ اگر از آخرین اجرا ۲۴ ساعت گذشته باشد و سیاست روشن باشد، خودش اجرا می‌کند |

هر اجرا در فید فعالیت با نوع `retention.applied` و تعداد رکوردها ثبت می‌شود، و «آخرین اجرا / تعداد رکورد» در همان کارت می‌ماند.

### آزمایش بدون انتظار

برای دیدن نتیجه، لازم نیست یک سال صبر کنید: در فراخوانی مستقیم API می‌توان پنجره را برای همان اجرا کوتاه کرد.

```bash
# چه چیزی حذف/ناشناس می‌شود؟ (هیچ تغییری نمی‌دهد)
curl -X POST -H "X-Hovida-Session: …" -H "Content-Type: application/json" \
  -d '{"dryRun":true,"days":0}' https://hovida.example.ir/api/org/retention/run

# همان را واقعاً اجرا کن
curl -X POST -H "X-Hovida-Session: …" -H "Content-Type: application/json" \
  -d '{"days":0}' https://hovida.example.ir/api/org/retention/run
```

`days` در بدنهٔ درخواست، **سیاست ذخیره‌شده را تغییر نمی‌دهد**؛ فقط برای همان اجرا است.

## ۲) درخواست دادهٔ شخصی (DSAR)

**پروندهٔ کارجو › تب «اطلاعات بیشتر» › بخش «دادهٔ شخصی کارجو»**

### «دریافت همهٔ داده‌ها»

یک فایل JSON با این بخش‌ها دانلود می‌شود:

```
workspace          نام و شناسهٔ فضای کاری
candidate          رکورد کامل (بدون متن استخراج‌شده، جدا آمده)
job                 فرصت شغلی مربوط
resumeText          متن استخراج‌شدهٔ رزومه (اگر هنوز نگه داشته شده)
notes               یادداشت‌های تیم، با نویسنده و زمان
interviews          مصاحبه‌ها (زمان، مصاحبه‌گران، لینک جلسه)
offers              پیشنهادهای شغلی و امضای کارجو
messages.emails     ایمیل‌های فرستاده‌شده از صندوق سازمان
messages.sms        پیامک‌های فرستاده‌شده
scorecards          کارت‌های ارزیابی مصاحبه‌گران
schedulingLinks     لینک‌های انتخاب زمان
activity            هر خط فید فعالیت که به این کارجو مربوط است
exportedAtISO / exportedAtJalali
```

فایل برای همان کارجو و فقط با نقش مدیر تولید می‌شود.

### «پاک‌سازی کامل داده»

پس از تأیید در پنجرهٔ گفت‌وگو، سرور همهٔ ردیف‌های مرتبط را حذف می‌کند و تعداد حذف‌شده‌ها را برمی‌گرداند:

```json
{ "erased": { "resumes": 1, "notes": 2, "interviews": 1, "offers": 0, "messages": 3,
              "scorecards": 1, "links": 0, "automations": 0 } }
```

* بدون `{"confirm":"ERASE"}` هیچ کاری انجام نمی‌شود (پاسخ `400`).
* فقط مدیر؛ عضو تیم `403` می‌گیرد.
* یک خط در فید فعالیت می‌ماند: «به درخواست حذف دادهٔ شخصی، همهٔ اطلاعات «…» را پاک کرد» — خود این خط نام کارجو را دارد؛ اگر می‌خواهید آن هم نماند، از **حذف کامل رکورد** (تنظیمات › نگه‌داری داده) استفاده کنید یا در حذف دستی، پیش از پاک‌سازی خروجی بگیرید.

## ۳) چه چیزی این کار نیست

| نیست | توضیح |
| --- | --- |
| گواهی انطباق حقوقی | این ابزارها **اجرای** سیاست شما هستند، نه خودِ سیاست. اینکه چند روز نگه دارید، چه کسی مسئول پاسخ به درخواست است و چگونه هویت درخواست‌کننده را احراز می‌کنید، تصمیم سازمان شماست. |
| حذف از پشتیبان‌ها | پشتیبان‌گیری فایل کامل پایگاه داده است (`/admin › پشتیبان`). حذف در سامانهٔ فعال، پشتیبان‌های قبلی را تغییر نمی‌دهد؛ برای حذف کامل باید چرخهٔ عمر پشتیبان هم سیاست داشته باشد. |
| حذف از سامانه‌های بیرونی | اگر کارجو را با API یا وب‌هوک به HRIS فرستاده‌اید، پاک‌سازی در هویدا آن سامانه را تغییر نمی‌دهد. |
| گزارش «چه کسی چه داده‌ای دید» | لاگ دسترسی به تکتک فیلدها وجود ندارد؛ فید فعالیت، اقدام‌ها را ثبت می‌کند نه بازدیدها. |

## ۴) پیشنهاد عملی برای شروع

1. در **تنظیمات › سازمان › نگه‌داری داده**: ۳۶۵ روز، **ناشناس‌سازی**.
2. «اجرای آزمایشی» را بزنید تا ببینید امروز چند رکورد مشمول می‌شود (معمولاً صفر، چون داده تازه است).
3. در قرارداد یا سیاست داخلی بنویسید: «دادهٔ کارجویان ردشده حداکثر یک سال پس از آخرین تماس ناشناس می‌شود؛ درخواست حذف ظرف ۳۰ روز اجرا می‌شود.»
4. برای هر درخواست حذف، اول «دریافت همهٔ داده‌ها» و بعد «پاک‌سازی کامل» — همان ترتیبی که در پنجرهٔ تأیید هم آمده است.
