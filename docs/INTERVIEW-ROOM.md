# اتاق مصاحبهٔ زنده

> **چکیده:** یک لینک برای هر جلسهٔ مصاحبه، بدون نصب هیچ برنامه‌ای: کارجو لینک را
> باز می‌کند، دوربین را روشن می‌کند و تماس **مستقیم بین دو مرورگر** برقرار می‌شود
> (WebRTC). سرور هویدا تصویر و صدا را نمی‌بیند، ذخیره نمی‌کند و ضبط نمی‌کند؛ فقط چند
> پیام کوتاهِ آدرس‌دهی (SDP و ICE) را رد و بدل می‌کند.

مسیر: **فرصت شغلی ← مصاحبه‌ها ← «اتاق زنده»** · صفحهٔ تماس: `/room/<توکن>`

---

## ۱. چه چیزی از سرور می‌گذرد و چه چیزی نه؟

| می‌گذرد | نمی‌گذرد |
| --- | --- |
| `offer` / `answer` (SDP، چند کیلوبایت متن) | تصویر دوربین |
| `ice` (نامزدهای اتصال، JSON کوچک) | صدای میکروفون |
| `bye` (پایان تماس) | هیچ فایل ضبط‌شده‌ای |
| حضور دو طرف (وقتی آخرین بار دیده شدند) | هیچ سابقه‌ای از مکالمه |

پیام‌ها **فقط در حافظه** می‌مانند: با ری‌استارت سرور، اتاق خالی می‌شود و هر دو طرف
دوباره وصل می‌شوند. در فایل ذخیره هم هیچ SDP‌ای نوشته نمی‌شود (آزمون خودکار همین را
بررسی می‌کند).

## ۲. سه کلیک تا تماس

1. جلسه را در پنل کارجو ثبت کنید (تاریخ/ساعت شمسی، مدت، مصاحبه‌گر).
2. در فهرست مصاحبه‌ها → **«اتاق زنده»** — اتاق ساخته و **لینکش کپی** می‌شود.
3. همان لینک را برای کارجو بفرستید (ایمیل یا پیامک خودتان). مصاحبه‌گر همان صفحه را
   از داخل برنامه باز می‌کند؛ چون نشست دارد، نقش «مصاحبه‌گر» می‌گیرد و کارجو نقش خودش.

هر دو طرف دکمهٔ **«روشن‌کردن دوربین و پیوستن»** را می‌زنند؛ تماس به‌محض دیده‌شدن
طرف مقابل خودش برقرار می‌شود (مصاحبه‌گر پیشنهاد می‌دهد، کارجو پاسخ می‌دهد).

## ۳. قاعده‌های سرور

| قاعده | رفتار |
| --- | --- |
| یک اتاق برای هر جلسه | کلیک دوم همان لینک را برمی‌گرداند (`reused: true`) — هیچ‌وقت دو لینک زنده |
| نقش را سرور تعیین می‌کند | توکن فقط می‌تواند «کارجو» باشد؛ فیلد `from` از مرورگر نادیده گرفته می‌شود |
| طول پیام | حداکثر ۲۴٬۰۰۰ نویسه، ۴۰۰ پیام در حافظه؛ بیشتر → `413` |
| نوع پیام | فقط `offer`، `answer`، `ice`، `bye` — بقیه → `400 BAD_SIGNAL_KIND` |
| اعتبار | ۴ ساعت بعد از ساعت جلسه (یا ۴ ساعت از حالا اگر گذشته باشد) → `410 ROOM_EXPIRED` |
| بستن | دکمهٔ «پایان و بستن اتاق» → `410 ROOM_CLOSED` برای هر پیام تازه |
| جلسهٔ لغوشده | اتاق تازه نمی‌گیرد (`409 INTERVIEW_CANCELLED`) |
| غربالگری بی‌طرف | ساختن اتاق و حتی ادامهٔ اتاق باز، بسته می‌شود (`409 BLIND_REVEAL_REQUIRED`) |
| حذف دادهٔ کارجو | اتاق‌ها پاک و در شمارش `erased.rooms` گزارش می‌شوند |
| فضای کاری دیگر | ۴۰۴ برای فهرست، پیام، بستن و جست‌وجو با توکن |

## ۴. شبکه: چیزی که باید صادقانه گفت

اتصال **مستقیم** است و برای آنکه دو مرورگر همدیگر را پیدا کنند، حداقل یک سرور STUN
لازم است. پیش‌فرض:

```
stun:stun.l.google.com:19302 · stun:stun.cloudflare.com:3478
```

با متغیر محیطی `ROOM_ICE_SERVERS` می‌توانید سرور خودتان را بدهید (JSON آرایه‌ای،
همان شکل `RTCPeerConnection`):

```bash
ROOM_ICE_SERVERS='[{"urls":"stun:stun.example.ir:3478"}]'
```

**آنچه نداریم:** سرور **TURN** (رلهٔ ترافیک). معنی‌اش این است:

- در بیشتر شبکه‌های خانگی و موبایل، اتصال برقرار می‌شود؛
- پشت NAT متقارن یا فایروال شرکتیِ سخت‌گیر، اتصال **برقرار نمی‌شود** و صفحه همین را
  می‌گوید («شبکه اجازه نداد») و تماس تلفنی را پیشنهاد می‌کند؛
- راه‌حل، یک سرور TURN است (coturn روی یک VPS). چون هزینهٔ پهنای باند دارد، به‌عنوان
  سرویس پیش‌فرض نمی‌فروشیم؛ با `ROOM_ICE_SERVERS` می‌توانید خودتان وصل کنید.

این تنها بخشی از محصول است که «کار می‌کند، اما نه روی هر شبکه‌ای» — و همین جمله در
صفحهٔ تماس هم نوشته شده است.

## ۵. حریم خصوصی

- **هیچ ضبطی وجود ندارد** — نه ویدئو، نه صدا، نه رونویسی خودکار از تماس زنده.
  (رونویسی در هویدا از فایل یا متن دستی است: [`TRANSCRIPTS.md`](TRANSCRIPTS.md).)
- پیام‌های اتاق بعد از پایان تماس بی‌ارزش‌اند و با ری‌استارت پاک می‌شوند.
- صفحه هیچ امتیاز، یادداشت یا دادهٔ دیگری از پروندهٔ کارجو دریافت نمی‌کند؛ فقط نام،
  عنوان موقعیت، نام سازمان، ساعت جلسه و لینک.
- کارجو با هیچ حسابی وارد نمی‌شود؛ توکن تصادفی ۲۴ بایتی تنها کلید است.

## ۶. API

```http
POST /api/interviews/:id/room        → 201 { room, reused }     (تکرار → 200)
GET  /api/rooms?interviewId=…        → { items }
GET  /api/rooms/by-token/:token      → { room }                 (فقط میزبان)
POST /api/rooms/:id/close            → { room }
GET  /api/rooms/:id/signals?since=N  → { seq, items, presence, status, closedReason }
POST /api/rooms/:id/signal           body: { kind, payload }    (from = host)

GET  /api/rooms/public/:token        → { room, state }          (بدون نشست)
GET  /api/rooms/public/:token/signals?since=N
POST /api/rooms/public/:token/signal body: { kind, payload }    (from = candidate)
POST /api/rooms/public/:token/leave
```

`since` یک نشانگر است: هر بار فقط پیام‌های بعد از آخرین `seq` برمی‌گردند، پس هیچ
پیامی دوبار مصرف نمی‌شود.

## ۷. آزمون

```bash
npm run test:room        # ۶۳ بررسی
```

پوشش: ساخت اتاق از جلسه و یکتایی لینک، باز شدن بدون نشست، STUN و جملهٔ صادقانهٔ رله،
نبود هر دادهٔ حساس در پاسخ عمومی، حضور دو طرف، رد و بدل offer/answer/ice با نشانگر
درست، **جلوگیری از جعل نقش میزبان با توکن**، سقف اندازه و نوع پیام، بستن توسط منابع
انسانی (`410`)، توضیح اتاق بسته به‌جای صفحهٔ خالی، ساخت اتاق تازه برای جلسهٔ دیگر،
جداسازی فضاهای کاری، بسته‌شدن در حالت بی‌طرف، لغو جلسه، حذف دادهٔ کارجو با شمارش
`erased.rooms`، و اینکه هیچ SDP‌ای در فایل ذخیره نوشته نمی‌شود.

آنچه در Node قابل آزمون نیست و فقط با دو مرورگر واقعی دیده می‌شود: برقراری خودِ
جریان ویدئو/صدا. منطق آن در `src/pages/InterviewRoom.tsx` است و شکست اتصال، در همان
صفحه به‌صورت شفاف گزارش می‌شود.

## ۸. آنچه هنوز نیست

- **رلهٔ TURN خودمان** (بخش ۴): نیاز به سرور و پهنای باند.
- **اتاق چندنفره** (پنل سه‌نفره یا بیشتر) — امروز یک‌به‌یک است؛ سه‌نفره با mesh
  و بدون SFU کیفیت را پایین می‌آورد و صادقانه نیست که «پشتیبانی می‌شود» بگوییم.
- **اشتراک صفحه** و **چت متنی کنار تماس**.
- **ضبط با رضایت صریح دو طرف** — عمداً نیست؛ افزودنش نیازمند رضایت ثبت‌شده و سیاست
  نگه‌داری جداگانه است.
