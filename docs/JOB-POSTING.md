# آگهی شغلی برای گوگل (schema.org `JobPosting`) و مهلت درخواست

پورتال شغلی هویدا فقط یک صفحهٔ زیبا نیست: هر آگهی منتشرشده، نشانه‌گذاری استاندارد
[`schema.org/JobPosting`](https://schema.org/JobPosting) دارد که «گوگل برای مشاغل» (Google for Jobs)
و هر جمع‌کنندهٔ دیگری می‌تواند بخواند. این کار در سرور انجام می‌شود — نه در مرورگر — چون خزنده‌ها
منتظر اجرای جاوااسکریپت نمی‌مانند.

## چه چیزی ساخته می‌شود

| نشانی | چه می‌دهد |
| --- | --- |
| `/careers/<slug>/jobs/<jobId>` | صفحهٔ آگهی با `<script type="application/ld+json">` در `<head>` |
| `/careers/<slug>` | فهرست فرصت‌ها با یک `ItemList` (نه چند `JobPosting` روی یک صفحه) |
| `/careers/<slug>/job-posting.json` | همان داده‌ها به‌صورت JSON خام — برای جمع‌کننده یا سایت خودتان |
| `/careers/<slug>/sitemap.xml` | نقشهٔ سایت همان پورتال، برای اینکه موتور جست‌وجو خودش همه را پیدا کند |
| `/api/careers/<slug>/jobs/<jobId>` | نسخهٔ API همان صفحه (شامل `expired` و `applyByJalali`) |

## نقشهٔ فیلدها

| فیلد `JobPosting` | از کجا می‌آید |
| --- | --- |
| `title` | عنوان فرصت شغلی |
| `description` | «شرح شغل و نکات مهم» (اگر خالی باشد، توضیح سادهٔ معیارها) — متن به سطر و فهرست تبدیل می‌شود |
| `datePosted` | لحظهٔ انتشار در پورتال |
| `validThrough` | «مهلت درخواست»، پایان همان روز به وقت تهران — و فقط وقتی مهلتی واقعاً تعیین شده باشد |
| `hiringOrganization.name` / `sameAs` | نام سازمان و نشانی پورتال خودش |
| `jobLocation.address` | `addressLocality` = محل کار، `addressCountry` = `IR` |
| `employmentType` | تمام‌وقت / پاره‌وقت / قراردادی / دورکاری / ترکیبی / کارآموزی → `FULL_TIME`، `PART_TIME`، `CONTRACTOR`، `INTERN` |
| `jobLocationType` | برای «دورکاری»: `TELECOMMUTE` |
| `identifier` | شناسهٔ همان فرصت شغلی |
| `url` | نشانی همان صفحه |
| `directApply` | همیشه `true` — فرم درخواست روی همین صفحه است، نه یک سایت واسط |

هیچ فیلدی حدس زده نمی‌شود: حقوق (`baseSalary`) تا وقتی فیلد حقوق در محصول نباشد منتشر نمی‌شود،
و `validThrough` برای فرصت بی‌مهلت ساخته نمی‌شود (تاریخ ساختگی یعنی اعلام اشتباه پایان آگهی).

## مهلت درخواست

در صفحهٔ فرصت شغلی → «ویرایش اطلاعات» → **مهلت درخواست (شمسی)** (مثلاً `۱۴۰۴/۰۸/۱۲`).
خالی گذاشتن یعنی «تا اطلاع ثانوی».

پس از پایان آن روز:

- آگهی از فهرست پورتال، از `sitemap.xml` و از `job-posting.json` برداشته می‌شود؛
- صفحهٔ آگهی باز می‌ماند (پیوندی که کسی فرستاده نباید به ۴۰۴ برسد) ولی با پیام روشن
  «مهلت درخواست این فرصت تمام شده است» و بدون فرم؛
- نشانه‌گذاری `JobPosting` حذف و `robots: noindex` جای آن گذاشته می‌شود؛
- ثبت درخواست با کد `410 APPLICATION_CLOSED` رد می‌شود.

## راه‌اندازی در سمت گوگل

۱. پورتال را روی دامنهٔ واقعی منتشر کنید (`PUBLIC_URL` را هم اگر پشت پروکسی هستید بگذارید).
۲. `https://<دامنه>/careers/<slug>/sitemap.xml` را در Google Search Console ثبت کنید.
۳. در [Rich Results Test](https://search.google.com/test/rich-results) همان نشانی آگهی را بررسی کنید؛
   باید «Job posting» سبز باشد.
۴. بعد از انتشار، در Search Console بخش «Job postings» نتیجه را ببینید.

> گوگل یک خطای رایج دارد: «Job posting has expired». علتش همان `validThrough` است که تاریخش گذشته —
> در هویدا این حالت خودکار مدیریت می‌شود و آگهی از فهرست برداشته می‌شود، پس چیزی برای تعمیر نمی‌ماند.

## جمع‌کننده‌های ایرانی (Jobinja، Jobvision، ای‌استخدام، Quera، IranTalent)

هویدا داده را آماده و استاندارد منتشر می‌کند، اما این سایت‌ها آگهی را از طریق **قرارداد B2B** یا
پنل خودشان می‌گیرند و API عمومی برای ثبت آگهی نمی‌دهند. دو مسیر صادقانه وجود دارد:

- `job-posting.json` را به‌عنوان منبع به آن‌ها بدهید (بسیاری برای همگام‌سازی همین را می‌پذیرند)؛
- یا آگهی را در پنل خودشان ثبت کنید و همان متن را از هویدا کپی کنید.

هنگامی که قرارداد و دسترسی API برقرار شد، اتصالش در همان صفحهٔ «کلیدها و اتصال‌ها» به‌عنوان یک
کلید تازه اضافه می‌شود؛ تا آن روز هیچ موفقیت جعلی نمایش داده نمی‌شود.

## «انتشار در جاب‌بورد» — متن آماده و ثبت این‌که کجا رفت

تب **«انتشار»** در صفحهٔ هر فرصت شغلی، همان دو مسیر بالا را به یک کار روزمره تبدیل می‌کند:

- برای هر جاب‌بورد یک **متن آماده** ساخته می‌شود (عنوان، دپارتمان، محل، نوع همکاری، مهلت، شرح
  شغل و **لینک درخواست روی صفحهٔ استخدام خودتان**). یک کلیک کپی، و در فرم جاب‌بورد بچسبانید.
- کنارش `JobPosting` همان آگهی هم هست، برای جمع‌کننده‌ای که JSON می‌خواهد.
- سپس **ثبت** می‌کنید: کدام جاب‌بورد، با چه لینکی، چه روزی و توسط چه کسی؛ وضعیتش
  «منتشر شده / برداشته شد / منقضی» می‌شود و تاریخ برداشتن هم می‌ماند.
- اگر فیلدی را جاب‌بورد می‌پرسد و ما نداریم (محل کار، نوع همکاری، شرح شغل، لینک درخواست)،
  همان‌جا فهرست می‌شود — حدس زده نمی‌شود.

```http
GET   /api/job-boards                              → { items, note }   (کاتالوگ + شرط هر بورد)
GET   /api/jobs/:id/publications                   → { items, boards, portalUrl, readyToPost, counts }
GET   /api/jobs/:id/publication-kit?board=jobinja  → { kit: { text, jsonLd, missing, requires } }
POST  /api/jobs/:id/publications                   body: { board, url?, note?, status? }
PATCH /api/publications/:id                        body: { status?, url?, note? }
DELETE /api/publications/:id                       (فقط برای ثبت اشتباه؛ برداشتن = وضعیت)
```

**چرا دکمهٔ «انتشار خودکار» نیست:** هیچ‌کدام از این پنج بورد رابط نوشتن عمومی ندارد؛ انتشار
یعنی حساب کارفرما و قرارداد. دکمه‌ای که چیزی نمی‌فرستد بدتر از نبودنش است، پس صفحه صریح
می‌گوید: «متن می‌دهیم، ثبت می‌کنیم؛ فرستادن با شماست.» روزی که قرارداد و API برقرار شد، همان
مسیر (`POST /jobs/:id/publications`) می‌تواند ارسال واقعی هم انجام دهد — بدون تغییر شکل محصول.

## آزمون

```bash
npm run test:jobposting
```

۴۶ بررسی: نشانه‌گذاری در HTML سرور، تطابق فیلدها با دادهٔ واقعی، `ItemList` در فهرست،
`validThrough` از مهلت، بسته‌شدن فرم بعد از مهلت، خروج از نقشهٔ سایت، و اینکه یک
`</script>` در متن آگهی نمی‌تواند از بلوک JSON بیرون بزند.
