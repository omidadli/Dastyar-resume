# گردش تأیید پیشنهاد شغلی

> **چکیده:** در بسیاری از سازمان‌ها منابع انسانی نمی‌تواند پیشنهاد شغلی را تنها بفرستد: مدیر فنی،
> مالی و مدیرعامل باید به ترتیب تأیید کنند. هویدا این زنجیره را روی **هر پیشنهاد** می‌نشاند،
> دکمهٔ ارسال را تا تأیید مرحلهٔ فعلی می‌بندد، و رد شدن یک مرحله را با دلیل ثبت می‌کند.
>
> پیش‌فرض **خاموش** است: تیم کوچک نباید بدون خواستن، یک قدم اضافه در مسیر استخدام ببیند.

مسیر تنظیم: **تنظیمات ← سازمان ← «گردش تأیید پیشنهاد»**
مسیر استفاده: **پروندهٔ کارجو ← پیشنهاد شغلی**.

---

## ۱. راه‌اندازی (یک دقیقه)

1. در **تنظیمات ← سازمان** کلید «گردش تأیید پیشنهاد» را روشن کنید.
2. برای هر مرحله یک **برچسب** («مدیر فنی»، «مالی»، «مدیرعامل») و یک **تأییدکننده** از اعضای
   همان فضای کاری انتخاب کنید. حداکثر سه مرحله، به ترتیب از بالا به پایین.
3. **ذخیره**.

قواعد سرور روی همین ذخیره:

| قاعده | پیام |
| --- | --- |
| زنجیرهٔ روشن بدون تأییدکننده ذخیره نمی‌شود | «دست‌کم یک تأییدکننده از اعضای تیم انتخاب کنید.» |
| یک نفر در دو مرحلهٔ پیاپی مجاز نیست | «ترتیب را یک‌نفره بچینید.» |
| تأییدکننده باید عضو همین فضای کاری باشد | مرحلهٔ غیرعضو در ذخیره حذف می‌شود |
| فقط مدیر یا مالک تنظیم می‌کند | ۴۰۳ برای بقیه |
| هر تغییر در تاریخچه ثبت می‌شود | «گردش تأیید پیشنهاد را روشن کرد (۲ مرحله)» |

---

## ۲. رفتار روی هر پیشنهاد

- **زنجیره در لحظهٔ ساخت روی پیشنهاد کپی می‌شود.** اگر فردا زنجیره را عوض کنید، پیشنهاد
  در جریان دست‌نخورده می‌ماند — تاریخچه بازنویسی نمی‌شود.
- **«ارسال با ایمیل سازمان» تا تأیید همهٔ مراحل کار نمی‌کند:** پاسخ
  `409 { code: "OFFER_APPROVAL_PENDING" }` با نام همان کسی که منتظرش هستیم.
- **هر مرحله فقط در اختیار همان فرد است.** مدیر و مالک می‌توانند به‌جای او تصمیم بگیرند و
  همین در متن تاریخچه می‌آید: «(به‌جای «…»)، با یادداشت «…»».
- **رد شدن، پیشنهاد را می‌بندد:** وضعیت «لغو‌شده» و دلیل در همان مرحله می‌ماند. اگر ارزشش را
  داشت، پیشنهاد تازه بسازید (بدون کپی خودکار شرایط — آگاهانه).
- **تأیید آخر، ارسال را آزاد می‌کند**؛ پیشنهاد همچنان پیش‌نویس است تا کسی دکمهٔ ارسال را بزند
  (هیچ ایمیلی خودکار نمی‌رود).
- **خاموش‌کردن زنجیره** فقط روی پیشنهادهای **تازه** اثر دارد.

جایی که تأییدکننده می‌بیند: همان دیالوگ پیشنهاد شغلی در پروندهٔ کارجو — فهرست مراحل با
وضعیت و تاریخ، کادر یادداشت، و دو دکمهٔ «تأیید این مرحله» / «رد پیشنهاد».

---

## ۳. داده‌ای که ذخیره می‌شود

روی هر پیشنهاد:

```json
"approvals": [
  { "id": "s1", "label": "مدیر فنی", "approverId": "usr_…", "approverName": "نگار رضایی",
    "status": "approved", "decidedAtISO": "2026-10-30T…", "decidedAtJalali": "۱۴۰۵/۰۸/۰۸", "note": null },
  { "id": "s2", "label": "مدیرعامل", "approverId": "usr_…", "approverName": "…",
    "status": "pending", "decidedAtISO": null, "decidedAtJalali": null, "note": null }
]
```

تنظیم سازمان (`GET /api/org` → `org.offerApproval`) فقط شناسه‌ها و برچسب‌ها را نگه می‌دارد؛
نام افراد در زمان خواندن از فهرست اعضا حل می‌شود.

---

## ۴. مسیرهای HTTP

```http
GET   /api/org          → { org, members }            (org.offerApproval)
PATCH /api/org          body: { offerApproval: { enabled, steps: [{ id, label, approverId }] } }   (مدیر/مالک)
POST  /api/offers/:id/approval   body: { decision: "approved" | "rejected", note? }
```

خطاها: `APPROVAL_STEPS_REQUIRED`، `APPROVAL_DUPLICATE`، `NOT_YOUR_TURN` (۴۰۳)،
`APPROVAL_DONE`، `NOT_DRAFT`، `OFFER_APPROVAL_PENDING` (روی ارسال)، `BAD_DECISION`.

---

## ۵. چرا این‌طور ساخته شده (و چه چیزی نیست)

| تصمیم | دلیل |
| --- | --- |
| حداکثر سه مرحله | بیشتر از این، در عمل یعنی کمیته؛ سه سطح (فنی، مالی، نهایی) کافی است |
| کپی زنجیره روی پیشنهاد | تغییر تنظیمات نباید سرنوشت پیشنهادی را که در جریان است عوض کند |
| رد = بسته‌شدن پیشنهاد | «رد شد ولی می‌شود فرستاد» یعنی کنترل وجود ندارد |
| مدیر/مالک می‌تواند جای تأییدکننده تصمیم بگیرد | مرخصی و بیماری نباید استخدام را قفل کند؛ ولی نام او در تاریخچه می‌ماند |
| تصمیم با یادداشت اختیاری | دلیل رد در عمل اجباری است؛ در UI به آن تشویق می‌شود |

**نیست:** تأیید موازی (همه هم‌زمان)، نمایندهٔ جانشین خودکار، یا اتصال به سیستم امضای
سازمانی. هر سه با همین مدل داده قابل افزودن‌اند: موازی ۳–۵ روز، نماینده ۲ روز.
