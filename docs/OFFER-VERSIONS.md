# نسخه‌های پیشنهاد شغلی (مذاکره)

> **چکیده:** پس از ارسال پیشنهاد، کارجو تقریباً همیشه یک بار مذاکره می‌کند: حقوق، تاریخ شروع،
> دورکاری. در هویدا پیشنهادِ فرستاده‌شده **ویرایش نمی‌شود** (سند امضاشدنی است) و به‌جای آن
> **«نسخهٔ تازه»** ساخته می‌شود: نسخهٔ قبلی بسته و در تاریخچه نگه داشته می‌شود، نسخهٔ بعدی
> پیش‌نویس تازه‌ای است که باید تأیید و ارسال شود. لینک قبلی همان لحظه از کار می‌افتد تا هیچ‌وقت
> دو پیشنهاد زنده هم‌زمان وجود نداشته باشد.

مسیر استفاده: **پروندهٔ کارجو ← پیشنهاد شغلی ← «نسخهٔ تازه (مذاکره)»**

---

## ۱. مسئله‌ای که حل می‌کند

بدون نسخه‌بندی، سه راه بد وجود دارد:

| راه بد | چه می‌شکند |
| --- | --- |
| پیشنهاد فرستاده‌شده را ویرایش کنیم | کارجو یک سند دیده و روی چیز دیگری امضا کرده؛ سابقهٔ مذاکره پاک می‌شود |
| پیشنهاد دوم بسازیم و اولی را رها کنیم | دو لینک زنده؛ کارجو می‌تواند هر دو را بپذیرد و معلوم نیست کدام معتبر است |
| پیام «شفاهی» بگوییم و رقم را ایمیل کنیم | امضای الکترونیکی روی عدد توافق‌شده وجود ندارد |

هویدا راه چهارم را می‌رود: **زنجیرهٔ نسخه‌ها** — هر نسخه سند خودش است، لینک خودش را دارد و
فقط آخرین نسخه زنده است.

---

## ۲. سه کلیک

1. **پروندهٔ کارجو ← پیشنهاد شغلی** — پیشنهاد در وضعیت «فرستاده‌شده» است.
2. **«نسخهٔ تازه (مذاکره)»** → نسخهٔ ۲ به‌صورت **پیش‌نویس** باز می‌شود؛ شرایط نسخهٔ قبلی
   خودکار کپی می‌شوند تا فقط همان چیزی را عوض کنید که در مذاکره عوض شد.
3. شرط‌ها را ویرایش کنید → **ذخیرهٔ پیش‌نویس** → (اگر گردش تأیید روشن است، تأییدها را بگیرید) →
   **ارسال با ایمیل سازمان**.

کارجو ایمیل تازه با **لینک نسخهٔ ۲** می‌گیرد و روی صفحه‌اش برچسب «نسخهٔ ۲» می‌بیند.

---

## ۳. قاعده‌های سرور

| وضعیت پیشنهاد | «نسخهٔ تازه» |
| --- | --- |
| `draft` (پیش‌نویس) | ❌ `409 OFFER_NOT_REVISABLE` — پیش‌نویس را ویرایش کنید، نه نسخه‌سازی |
| `sent` (فرستاده‌شده) | ✅ نسخهٔ بعدی ساخته می‌شود |
| `accepted` / `declined` | ❌ پاسخ ثبت شده؛ نسخهٔ تازه معنا ندارد |
| `cancelled` | ❌ اول پیشنهاد تازه بسازید |
| `superseded` | ❌ نسخهٔ بسته دوباره باز نمی‌شود |

قاعده‌های دیگر:

- **هر فضای کاری فقط نسخه‌های خودش را می‌بیند** (۴۰۴ برای بقیه) و «دسترسی آگهی» هم اعمال می‌شود.
- **شرایط خالی، شرایط قبلی را پاک نمی‌کند:** اگر بدنه خالی بفرستید، عنوان/تاریخ/حقوق نسخهٔ
  قبل کپی می‌شود؛ عنوان یا تاریخ شروعِ خالی هم ۴۰۰ است.
- **نسخهٔ تازه هیچ امضایی با خود نمی‌برد:** `signatureName`، `sentAtISO` و پاسخ‌ها صفر می‌شوند.
- **نسخهٔ تازه خودش نامه نمی‌فرستد** — ساخت نسخه صفر ایمیل دارد؛ ارسال همچنان دستی است.

---

## ۴. لینک قبلی چه می‌شود؟

با ساختن نسخهٔ تازه، نسخهٔ قبلی `superseded` می‌شود و لینک عمومی‌اش همان لحظه می‌بندد:

```http
GET /api/offers/public/<token-نسخهٔ-قدیم>
410 { "code": "OFFER_SUPERSEDED",
      "error": "این نسخه از پیشنهاد جایگزین شده است. نسخهٔ تازه برای شما فرستاده می‌شود؛ اگر نرسید، از منابع انسانی بخواهید دوباره بفرستد." }
```

صفحهٔ عمومی همین متن را به کارجو نشان می‌دهد (به‌جای «پیدا نشد» گمراه‌کننده). پذیرش نسخهٔ
قدیم هم ممکن نیست: مسیر امضا فقط روی پیشنهاد `sent` کار می‌کند.

---

## ۵. گردش تأیید، دوباره

نسخهٔ تازه یعنی **شرایط تازه**، پس تأییدها از صفر شروع می‌شوند:

- زنجیرهٔ تأییدِ **همان لحظه** روی نسخهٔ جدید کپی می‌شود (ممکن است با زنجیرهٔ نسخهٔ قبلی
  فرق کند — همان که امروز معتبر است).
- تا تأیید آخر، ارسال نسخهٔ جدید هم بسته است: `409 OFFER_APPROVAL_PENDING`.
- «ویرایش پیش‌نویس» در نسخهٔ تازه، گردش تأیید را دوباره باز **نمی‌کند** (فقط نسخه‌سازی می‌کند).

جزئیات زنجیره: [`OFFER-APPROVAL.md`](OFFER-APPROVAL.md).

---

## ۶. داده‌ای که ذخیره می‌شود

سه فیلد تازه روی هر پیشنهاد:

```json
{ "version": 2,
  "supersedesId": "off_8f…",
  "supersededById": null }
```

و روی نسخهٔ بسته‌شده:

```json
{ "version": 1, "status": "superseded",
  "supersedesId": null, "supersededById": "off_9c…" }
```

فهرست نسخه‌ها با همان `GET /api/offers?resumeId=…` خوانده می‌شود؛ نسخه‌ها پاک نمی‌شوند تا
سابقهٔ مذاکره برای گزارش و داوری بماند. در تاریخچهٔ فعالیت هم یک سطر ثبت می‌شود:
«نسخهٔ ۲ پیشنهاد «…» برای «…» نوشته شد؛ نسخهٔ پیشین بسته شد».

---

## ۷. آنچه تست شده و آنچه هنوز نیست

`npm run test:offers` (۱۰۴ بررسی) علاوه بر جریان اصلی، این‌ها را واقعی اجرا می‌کند: نسخه‌سازی
پیش‌نویس رد می‌شود، نسخهٔ ۲ با کپی شرایط ساخته می‌شود، حداکثر یک نسخهٔ زنده می‌ماند، لینک قدیم
۴۱۰ می‌دهد، نسخهٔ جدید تا ارسال برای کارجو باز نیست، امضای نسخهٔ ۲ پذیرفته می‌شود، نسخه‌سازی
پیشنهاد امضاشده و نسخهٔ بسته رد می‌شود، و همهٔ نسخه‌ها بعد از ری‌استارت سرور می‌مانند.

هنوز ساخته نشده (صادقانه):

- **مقایسهٔ کنارِ همِ دو نسخه** در یک نما («چه چیزی عوض شد؟» به‌صورت جدول تفاضل).
- **پیشنهاد شمارنده از سمت کارجو** («این رقم را می‌پذیرم» به‌عنوان پیشنهاد متقابل) — فعلاً
  کارجو فقط در همان صفحه یادداشت می‌نویسد و منابع انسانی دستی نسخه می‌سازد.
- **پیوست فایل به نسخه** (مثلاً جدول مزایا) — پیوست‌ها روی ایمیل سازمان هست، نه روی خود سند.
