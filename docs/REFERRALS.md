# معرفی همکار و پاداش معرفی

معرفی همکار ارزان‌ترین استخدام هر سازمان است و در بیشتر سیستم‌های استخدام، همان چیزی است که
فراموش می‌شود: نه پیگیری می‌شود، نه پاداشی برایش ثبت می‌شود. هویدا این حلقه را می‌بندد —
از لینکی که همکار می‌فرستد تا لحظه‌ای که پاداش پرداخت می‌شود.

## مسیر کامل در سه گام

**۱. روشن‌کردن برنامه** — تنظیمات › سازمان › کارت **«معرفی همکار و پاداش»**:

| فیلد | معنا |
| --- | --- |
| فعال باشد | تا روشن نشود، هیچ لینک معرفی‌ای ثبت نمی‌شود (فقط پاسخ «چطور با ما آشنا شدید؟» می‌ماند). |
| مبلغ پاداش (تومان) | صفر = پیگیری بدون پاداش نقدی؛ عدد = پاداش قابل پرداخت. |
| شرط پرداخت | «وقتی استخدام شد» / «وقتی پیشنهاد فرستاده شد» / «پس از دورهٔ آزمایشی». |
| شرایط پاداش | متنی که همکار می‌خواند (مثلاً پرداخت در فیش همان ماه). |
| فقط اعضای این فضای کاری | کدهای بیرون از سازمان پذیرفته نشوند. |

**۲. فرستادن لینک** — همان کارت، بخش «لینک معرفی هر همکار»: برای هر عضو یک کد و یک نشانی
مانند `https://hr.example.com/careers/company?ref=r476bc2c079` نشان داده می‌شود، با دکمهٔ کپی.

کد از `HMAC-SHA256(userId, APP_SECRET)` ساخته می‌شود: پایدار (بعد از ری‌استارت و انتقال سرور همان
می‌ماند) ولی از شناسهٔ کاربر قابل حدس نیست. کد هر عضو **فقط در همان فضای کاری** معنا دارد؛ کد
سازمان دیگر هیچ معرفی‌ای ثبت نمی‌کند.

**۳. پیگیری و پرداخت** — هر درخواستی که با کد بیاید، در همان کارت فهرست می‌شود:

```
در حال بررسی → استخدام شد
                    ↓
        پاداش «در انتظار تأیید»
                    ↓  (تأیید مدیر)
              «تأییدشده — آمادهٔ پرداخت»
                    ↓  (ثبت پرداخت)
                  «پرداخت شد»
```

- **هیچ پاداشی خودکار پرداخت نمی‌شود.** «تأیید» و «ثبت پرداخت» دو کلیک انسانی جدا هستند، دقیقاً
  همان قاعده‌ای که برای ایمیل و پیامک کارجو رعایت می‌شود.
- کارجوی کنارگذاشته‌شده، پاداش در انتظار را **خودکار لغو** می‌کند (کسی برای استخدام‌نشده پول نمی‌گیرد).
- پاداش پرداخت‌شده قابل حذف نیست؛ برای اصلاح، یادداشت ثبت می‌شود (سابقهٔ مالی دست‌کاری نمی‌شود).
- شرط «پس از دورهٔ آزمایشی» عمداً دستی است: فقط یک انسان می‌داند فرد ماند یا رفت. دکمهٔ
  «دورهٔ آزمایشی گذشت — پاداش بدهکار شد» همان لحظه را ثبت می‌کند.

## API

| مسیر | کار |
| --- | --- |
| `GET /api/referrals` | برنامه، همهٔ معرفی‌ها، لینک هر عضو و خلاصهٔ مبالغ |
| `PUT /api/referrals/program` | روشن/خاموش، مبلغ، شرط، شرایط (فقط مدیر) |
| `POST /api/referrals/:id/approve` | در انتظار تأیید → تأییدشده (فقط مدیر) |
| `POST /api/referrals/:id/confirm` | پایان دورهٔ آزمایشی → در انتظار تأیید (فقط مدیر) |
| `POST /api/referrals/:id/pay` | تأییدشده → پرداخت‌شده (فقط مدیر) |
| `POST /api/referrals/:id/void` | لغو پاداشِ پرداخت‌نشده (فقط مدیر) |

## ارتباط با گزارش‌ها

- **منبع استخدام:** کارجویی که با کد معتبر آمده، منبعش `referral` است و در گزارش «منبع استخدام»
  جدا از پورتال شمرده می‌شود. کد نامعتبر منبع را تغییر نمی‌دهد (پاسخ خود کارجو در `heardFrom` می‌ماند).
- **هزینهٔ هر استخدام:** لحظه‌ای که «ثبت پرداخت» زده می‌شود، همان مبلغ به‌صورت خودکار با نوع
  هزینهٔ «پاداش معرفی» و به نام همان فرصت شغلی در گزارش هزینه ثبت می‌شود — مدیر مالی دوباره عدد
  وارد نمی‌کند و هزینهٔ هر استخدام خودش دقیق می‌ماند.

## آزمون

```bash
npm run test:referrals
```

۴۵ بررسی سرتاسری: کد معتبر و نامعتبر، برنامهٔ خاموش، ثبت معرفی، حرکت در قیف،
`pending → approved → paid`، جلوگیری از پرداخت بدون تأیید، لغو خودکار با کنارگذاشتن کارجو،
شرط دورهٔ آزمایشی، جداسازی فضاهای کاری، دسترسی فقط-مدیر، ثبت خودکار هزینه و ماندگاری بعد از ری‌استارت.
