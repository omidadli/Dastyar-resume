# همگام‌سازی اعضا با SCIM 2.0

سازمان‌های بزرگ اجازه نمی‌دهند یک ابزار تازه، فهرست کارکنان را جدا نگه دارد. هویدا استاندارد
**SCIM 2.0** را پیاده کرده تا ساخت، تغییر نام/عنوان و **غیرفعال‌سازی** افراد از همان‌جا انجام شود
که بقیهٔ حساب‌های شرکت مدیریت می‌شوند: Okta، Microsoft Entra ID یا Google Workspace.

## راه‌اندازی در سه گام

۱. **تنظیمات › توسعه‌دهندگان › همگام‌سازی اعضا با SCIM** › «صدور توکن SCIM».
   توکن یک بار نشان داده می‌شود (`hvd_scim_…`) و فقط هش آن ذخیره می‌شود.

۲. در سامانهٔ هویت، Provisioning را روشن کنید و این‌ها را وارد کنید:

| فیلد | مقدار |
| --- | --- |
| SCIM Base URL | `https://<دامنهٔ شما>/scim/v2` |
| Authentication | Bearer token (همان توکن) |
| Header | `Authorization: Bearer hvd_scim_…` |

۳. یک کاربر آزمایشی را Assign کنید و Sync را بزنید. اگر چیزی درست نبود، پاسخ خطا **دلیل** را
   می‌گوید (`uniqueness`، `invalidFilter`، `invalidPath`، `mutability`).

> صدور توکن تازه، توکن قبلی را **فوراً** باطل می‌کند. باطل‌کردن توکن، عضویت‌های موجود را تغییر نمی‌دهد.

## چه چیزی پشتیبانی می‌شود

| مسیر | کار |
| --- | --- |
| `GET /scim/v2/ServiceProviderConfig` | توانایی‌های واقعی (PATCH بله، Bulk نه) |
| `GET /scim/v2/ResourceTypes` · `/Schemas` | کشف منابع و صفات |
| `GET /scim/v2/Users?filter=userName eq "…"` | فهرست/جست‌وجو با `startIndex` و `count` |
| `GET /scim/v2/Users/:id` | یک کاربر |
| `POST /scim/v2/Users` | ساخت عضو (`userName` ایمیل، `displayName`/`name`، `title`، `roles`، `active`) |
| `PUT /scim/v2/Users/:id` | جایگزینی فیلدهای قابل تغییر |
| `PATCH /scim/v2/Users/:id` | `Operations` (شکل Okta و Entra) |
| `DELETE /scim/v2/Users/:id` | غیرفعال‌سازی + پایان نشست‌ها |
| `GET /scim/v2/Groups` · `/Groups/:id` | گروه‌های نقش: `owners`، `admins`، `members` |

### فیلترها

فقط دو فیلتر پذیرفته می‌شود — همان‌هایی که سامانه‌های هویت می‌فرستند:

- `userName eq "sara@example.com"`
- `externalId eq "<user id>"`

هر فیلتر دیگری `400 invalidFilter` می‌گیرد. نادیده‌گرفتن فیلتر یعنی همگام‌سازی افراد اشتباه؛ پس
هویدا ترجیح می‌دهد صریح شکست بخورد.

## قواعدی که عمداً این‌طور هستند

- **حذف = غیرفعال‌سازی.** `DELETE` کاربر را پاک نمی‌کند؛ `active: false` می‌شود و نشست‌هایش
  پایان می‌یابد. سابقهٔ استخدام، فعالیت‌ها و تصمیم‌ها می‌مانند و اشتباه سامانهٔ هویت برگشت‌پذیر است.
- **مالک فضای کاری دست‌نیافتنی است.** SCIM نمی‌تواند مالک بسازد، نقش مالک را تغییر دهد یا مالک را
  غیرفعال کند (`403 mutability`).
- **نقش «مدیر» فقط با توکن مالک.** اگر توکن را یک مدیر (نه مالک) صادر کرده باشد، SCIM فقط عضو
  می‌سازد و ارتقا به مدیر در هویدا انجام می‌شود. این جلوی یک IdP بدتنظیم را می‌گیرد.
- **هیچ رمزی از SCIM برنمی‌گردد.** کاربر تازه با رمز تصادفی ساخته می‌شود؛ ورودش از راه SSO است یا
  مدیر از «تنظیمات › تیم › تعیین رمز» برایش رمز می‌گذارد (رمز ساخته‌شده یک بار نشان داده می‌شود و
  نشست‌های قبلی بسته می‌شوند).
- **گروه‌ها فقط خواندنی‌اند.** گروه در هویدا یعنی نقش؛ ساخت گروه تازه یعنی ساختن مدل دسترسی‌ای که
  وجود ندارد. `POST/PATCH/DELETE /Groups` با `501 notImplemented` و توضیح روشن رد می‌شود؛ نقش را
  با `PATCH` روی خود کاربر عوض کنید.
- **هر تغییر در فعالیت‌ها ثبت می‌شود** با نام «SCIM (فراهم‌کنندهٔ هویت)» — تیم می‌بیند چه کسی و
  از کجا عضو اضافه یا غیرفعال شده است.
- `lastUsedISO` نشان می‌دهد آخرین فراخوانی سامانهٔ هویت کِی بوده است.

## آزمون

```bash
npm run test:scim
```
