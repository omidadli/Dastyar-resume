# ورود سازمانی (SSO با OIDC)

> **چکیده:** اعضای تیم با همان حسابی وارد می‌شوند که در سازمان دارند — Google Workspace،
> Microsoft 365 (Entra ID)، Okta یا یک Keycloak خودمیزبان. هویدا خودش را «ارائه‌دهندهٔ
> هویت» جا نمی‌زند: پروتکل استاندارد **OIDC** را پیاده می‌کند، بدون هیچ کتابخانهٔ بیرونی و
> بدون هیچ سرویس واسط. رمز سازمانی هرگز به هویدا نمی‌رسد؛ هویدا فقط امضای توکن را با کلید
> عمومی ارائه‌دهنده بررسی می‌کند.
>
> **همراهش:** «ورود دومرحله‌ای» ([`TWO-FACTOR.md`](TWO-FACTOR.md)) برای حساب‌هایی است که با
> رمز وارد می‌شوند. SSO و ۲FA رقیب هم نیستند: سازمان می‌تواند ۲FA را روی IdP خودش اجباری
> کند و هویدا فقط نتیجه را می‌بیند.

مسیر تنظیم: **تنظیمات ← اتصال‌ها ← کارت «ورود سازمانی (SSO)»** (فقط مدیر یا مالک).
مسیر ورود برای کارمند: **`/login` ← «ادامه با حساب سازمانی»**.

---

## ۱. چطور کار می‌کند (یک نگاه)

```
مرورگر                    هویدا (سرور)                     ارائه‌دهندهٔ هویت
   │  ایمیل سازمانی             │                                  │
   ├───────────────────────────►│ GET /api/auth/sso/lookup          │
   │  {available, orgName}      │ (فقط همین دو فیلد برمی‌گردد)      │
   │◄───────────────────────────┤                                  │
   │  «ادامه» ─────────────────►│ GET /api/auth/sso/start           │
   │                            │ state + nonce + PKCE، ذخیرهٔ موقت  │
   │  302 به صفحهٔ ورود سازمان ──┼─────────────────────────────────►│
   │                                                               │ ورود با حساب سازمان
   │◄──────────────────────────────────────────────────────────────┤ 302 با code
   ├───────────────────────────►│ GET /api/auth/sso/callback?code=  │
   │                            │ ── POST /token (با code + verifier) ──►│
   │                            │ ◄── id_token (RS256/ES256) ───────────┤
   │                            │ بررسی امضا با JWKS، iss/aud/exp/iat/nonce │
   │                            │ ساخت یا یافتن عضو، نشست             │
   │  302 به /app#sso=<token>   │                                  │
   │◄───────────────────────────┤  Referrer-Policy: no-referrer      │
```

نکتهٔ امنیتی: توکن نشست در **fragment** برمی‌گردد (`#sso=…`)، پس در لاگ سرور، در
`Referer` و در تاریخچهٔ مرورگر به‌عنوان مسیر دیده نمی‌شود.

## ۲. راه‌اندازی در سه دقیقه

### گام ۱ — یک اپلیکیشن OIDC در ارائه‌دهنده بسازید

همه‌جا یک الگو: نوع اپلیکیشن **Web application**، روش ورود **Authorization Code**، و یک
**Redirect URI** که دقیقاً برابر مقدار کارت هویدا باشد (پیش‌فرض:
`<آدرس سایت>/api/auth/sso/callback`).

| ارائه‌دهنده | Issuer | کجای کنسول |
| --- | --- | --- |
| Google Workspace | `https://accounts.google.com` | Google Cloud Console ← APIs & Services ← Credentials ← OAuth client (Web) |
| Microsoft 365 / Entra ID | `https://login.microsoftonline.com/<tenant-id>/v2.0` | Entra admin center ← App registrations ← Redirect URI (Web) |
| Okta | `https://<org>.okta.com` | Applications ← Create App Integration ← OIDC / Web |
| Keycloak (خودمیزبان) | `https://sso.company.ir/realms/<realm>` | Clients ← Create ← Client authentication ON |
| هر IdP دیگر | نشانی‌ای که `/.well-known/openid-configuration` زیر آن است | — |

### گام ۲ — در هویدا وارد کنید

**تنظیمات ← اتصال‌ها ← ورود سازمانی (SSO)**:

1. **ارائه‌دهنده** را از فهرست انتخاب کنید (یا «سفارشی» بگذارید و Issuer را دستی بزنید).
2. **Client ID** و **Client Secret** را بچسبانید. Secret رمزنگاری‌شده ذخیره می‌شود و هرگز
   به مرورگر برنمی‌گردد (پاسخ فقط «ذخیره شده است» می‌دهد).
3. **دامنه‌های ایمیل مجاز** را بنویسید؛ مثلاً `company.ir, company.com`. فقط همین
   دامنه‌ها از این مسیر وارد می‌شوند. با «،» یا فاصله جدا کنید.
4. **نقش عضو تازه** (عضو تیم یا مدیر) و دو کلید:
   - **ورود خودکار اعضای تازه** — روشن: هر کس ایمیل سازمانی معتبر دارد عضو می‌شود. خاموش:
     فقط کسانی که از قبل در فهرست تیم هستند.
   - **فقط ورود سازمانی** — روشن: برای دامنه‌های بالا رمز عبور پذیرفته نمی‌شود.
5. **بررسی اتصال** را بزنید. هویدا سند discovery را می‌خواند و شمار کلیدهای امضا را نشان
   می‌دهد. اگر ارائه‌دهنده پاسخ ندهد، **ذخیره هم انجام نمی‌شود** — تنظیم نیمه‌کاره نمی‌ماند.
6. **ذخیره**.

### گام ۳ — آزمایش

یک پنجرهٔ ناشناس باز کنید، `/login` بروید، ایمیل سازمانی را بزنید و «ادامه با حساب
سازمانی» را انتخاب کنید. اگر برگشتید به `/login?sso=…`، جدول زیر می‌گوید چرا.

## ۳. پیام‌های بازگشت (و معنای هر کدام)

| مقدار `?sso=` | معنا | اولین جایی که باید نگاه کنید |
| --- | --- | --- |
| `none` | برای این دامنه هیچ سازمانی SSO ندارد | دامنه در کارت SSO ثبت شده؟ |
| `misconfigured` | تنظیم ناقص یا نشانی ناامن | Issuer و Client ID؛ آیا https است؟ |
| `provider` | ارائه‌دهنده پاسخ نداد یا خطا داد | «بررسی اتصال»؛ وضعیت سرویس IdP |
| `expired` | ورود بیش از ۱۰ دقیقه طول کشید یا state مصرف شد | دوباره تلاش کنید (و ساعت سرور را چک کنید) |
| `off` | ورود سازمانی برای این سازمان خاموش شده | کارت SSO |
| `cancelled` | کاربر در صفحهٔ IdP انصراف داد | — |
| `code` | کد ورود رد شد (code/verifier جفت نبود) | Redirect URI دقیقاً ثبت شده؟ |
| `denied` | هویت پذیرفته نشد: ایمیل تأییدنشده، دامنهٔ دیگر، حساب سازمان دیگر، یا عضو دعوت‌نشده | `reason` در نشانی، و تاریخچهٔ فعالیت‌ها |
| `failed` | خطای غیرمنتظره | آخرین خطای کارت SSO و لاگ سرور |

`denied` همراه `reason` می‌آید: `SSO_DOMAIN`، `SSO_NOT_INVITED`، `SSO_OTHER_ORG`،
`ACCOUNT_DISABLED`، و برای توکنِ بی‌ایمیل یا ایمیل تأییدنشده `NO_EMAIL` و `EMAIL_UNVERIFIED`.

## ۴. قواعدی که سرور اعمال می‌کند

| قاعده | چرا |
| --- | --- |
| فقط `https` برای Issuer (به‌جز loopback) | توکن روی http قابل شنود است. برای Keycloak محلی `http://127.0.0.1:8080` مجاز است؛ `OIDC_ALLOW_HTTP=1` هم برای شبکهٔ داخلی آزمایشی وجود دارد |
| PKCE (S256) + `state` + `nonce` | کد رهگیری‌شده، CSRF بسته، و توکن دزدیده‌شده به نشست دیگر نمی‌خورد |
| هر `state` یک‌بارمصرف، عمر ۱۰ دقیقه | ورود نیمه‌کاره تبدیل به درِ باز نمی‌شود |
| امضا با کلید عمومی IdP، الگوریتم‌های RS256/384/512، PS256، ES256 | `alg: none` و کلیدهای نامعلوم رد می‌شوند؛ در صورت چرخش کلید، یک‌بار JWKS تازه گرفته می‌شود |
| `iss`، `aud`، `exp`، `iat`، `nonce` هر پنج بررسی می‌شوند | پذیرفتن توکنِ یک اپلیکیشن دیگر ممنوع |
| `email_verified` باید true باشد | ایمیل تأییدنشده یعنی کسی می‌تواند خودش را جای دیگری جا بزند |
| ایمیل عضوی از سازمان دیگر → ۴۰۹ | SSO نباید اجازه دهد نشست یک سازمان، عضو سازمان دیگر را بردارد |
| عضو غیرفعال → ۴۰۳ | تعلیق دستی، دستی می‌ماند |
| `autoJoin` خاموش → فقط اعضای موجود | کنترل دعوت دست نمی‌خورد |
| نقش از `defaultRole` است، هرگز `owner` | مالکیت سازمان با ورود سازمانی جابه‌جا نمی‌شود |
| حساب SSO رمز ندارد | یک رشتهٔ تصادفی scrypt ذخیره می‌شود که هیچ‌کس آن را نمی‌داند؛ ورود با رمز برای این حساب ممکن نیست |
| `lookup` فقط `{available, orgName, passwordBlocked}` برمی‌گرداند | شمارش اعضا و افشای تنظیمات سازمان از یک مسیر عمومی ممنوع |
| `lookup` محدودیت نرخ دارد | جلوگیری از شمارش دامنه |
| همهٔ ورودها در تاریخچه | «چه کسی، کِی، با چه روشی» |

هر ورود موفق `lastLoginAtISO` را به‌روز می‌کند و هر خطا `lastError` را — هر دو روی همان
کارت، پس پشتیبانی لازم نیست در لاگ بگردد.

## ۵. مسیرهای HTTP

عمومی (بدون نشست):

```http
GET /api/auth/sso/lookup?email=sara@company.ir
    → { available: true, orgName: "شرکت نمونه", passwordBlocked: false }

GET /api/auth/sso/start?email=sara@company.ir&next=/app/jobs
    → 302 به authorization_endpoint ارائه‌دهنده

GET /api/auth/sso/callback?code=…&state=…
    → 302 /app#sso=<token>       (موفق)
    → 302 /login?sso=<reason>    (ناموفق)
```

مدیریتی (نقش مدیر یا مالک):

```http
GET    /api/org/sso   → { sso }                        (بدون secret)
PUT    /api/org/sso   → { sso }     body: { enabled, issuer, clientId, clientSecret?, domains, autoJoin, defaultRole, requireSso }
DELETE /api/org/sso   → { ok }                          (قطع اتصال؛ نشست‌های موجود بسته نمی‌شوند)
POST   /api/org/sso/check → { ok, issuer, message, keys, authorizationEndpoint, tokenEndpoint }
                                                     (discovery + شمار کلید امضا؛ هیچ چیز ذخیره نمی‌شود)
```

جزئیات کامل در [`API.md`](API.md) §۵ج.

### خطاهای `PUT /api/org/sso`

پاسخ `400 { error, field }` است و `field` می‌گوید کدام کادر باید اصلاح شود:

| `field` | پیام |
| --- | --- |
| `issuer` | نشانی سرویس ورود سازمانی (Issuer) را وارد کنید. / نشانی باید با https شروع شود. / پیش از ذخیره باید سرویس ورود پاسخ بدهد: … |
| `clientId` | شناسهٔ برنامه (Client ID) را وارد کنید. |
| `clientSecret` | رمز محرمانهٔ برنامه (Client Secret) را وارد کنید. |
| `domains` | دست‌کم یک دامنهٔ ایمیل مجاز بنویسید؛ بدون آن هیچ‌کس نمی‌تواند وارد شود. |

`POST /api/org/sso/check` در خطا `400 { ok:false, message }` می‌دهد، نه `field` — چون چیزی
ذخیره نمی‌کند و فقط می‌خواهد بگوید چرا وصل نشد.

## ۶. اجرا در محیط واقعی

| متغیر | پیش‌فرض | کار |
| --- | --- | --- |
| `PUBLIC_URL` | `Origin` درخواست | ریشهٔ آدرس بازگشت؛ اگر پشت پراکسی هستید، حتماً ست کنید |
| `APP_SECRET` | — | کلید رمزنگاری Client Secret؛ تغییرش Secret را نامعتبر می‌کند (باید دوباره وارد شود) |
| `OIDC_ALLOW_HTTP` | خاموش | اجازهٔ http برای IdP داخلی؛ در تولید روشن نکنید |

پشت Nginx/Cloudflare، `X-Forwarded-Proto` را عبور بدهید تا آدرس بازگشت و کوکی‌ها درست
ساخته شوند. Redirect URI باید **دقیقاً** با آنچه در IdP ثبت شده یکی باشد (بدون `/` آخر).

---

## ۷. وقتی سازمان SSO را اجباری می‌کند

با «فقط ورود سازمانی» روشن:

- ورود با رمز برای ایمیل‌های همان دامنه‌ها با `403 {code:"SSO_REQUIRED"}` رد می‌شود؛
- عضوی که هنوز رمز دارد باید از SSO وارد شود، نه اینکه رمزش باطل شود (رمز برای روز
  قطعی IdP می‌ماند)؛
- مالک سازمان هم از این قاعده مستثنا نیست — و همین درست است، چون مسیر بازیابی همان IdP است;
- خاموش‌کردن کلید، بلافاصله رمز را برمی‌گرداند. لازم نیست چیزی ری‌ست شود.

## ۸. آنچه این پیاده‌سازی نیست (صادقانه)

| نیست | دلیل / مسیر |
| --- | --- |
| SAML 2.0 | OIDC همان نتیجه را با هزینهٔ کمتر می‌دهد و Google/Microsoft/Okta هر سه پشتیبانی می‌کنند. اگر مشتری فقط SAML دارد، آداپتور SAML حدود ۲ هفته است |
| SCIM (همگام‌سازی خودکار اعضا) | امروز عضویت از روی ورود ساخته می‌شود، نه از فهرست سازمان. SCIM نیازمند توکن مدیریتی IdP است: ۲ هفته |
| نقش‌ها از گروه‌های IdP | نقش از `defaultRole` می‌آید، نه از claim گروه. نگاشت گروه←نقش ۳–۵ روز |
| ورود سازمانی برای پورتال عمومی کارجو | کارجو مهمان است، نه عضو تیم؛ همان لینک عمومی و کد یک‌بارمصرف کافی است |

هیچ‌کدام از این‌ها «غیرممکن» نیستند؛ هر چهار مورد کار مشخص و زمان‌بندی‌شده‌اند.

## ۹. تست‌ها

- `npm run test:sso` — ۵۳ بررسی با یک ارائه‌دهندهٔ OIDC واقعیِ درون‌فرایندی (discovery،
  JWKS، authorize، token، امضای RS256، PKCE، توکن جعلی با کلید دوم، callback، ساخت عضو،
  قطع اتصال، ورود با رمز ممنوع، ماندگاری پس از ری‌استارت).
- `npm test` — بررسی‌های واحد توکن: امضای نادرست، `aud`، `exp`، `iss`، `nonce`، `alg=none`،
  `email_verified`، دامنه‌ها، و قاعدهٔ https.
- `npm run test:mount` — کارت SSO در تنظیمات و دکمهٔ ورود سازمانی در صفحهٔ ورود واقعاً رندر می‌شوند.
